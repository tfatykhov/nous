# Harness P2.8 — Compensation Registry + Reversible-Default Approval Nodes (design)

**Roadmap:** `docs/superpowers/plans/2026-09-24-harness-autonomy-roadmap.md` §5 ("P2.8 compensation
registry") and §2 row P2.8 ("No revert executor" — `compensation.handler` is free text never read;
no `review.revert` handler; nothing pushes an `action_review` automatically after a mutating call).
**Interacts with:** `docs/superpowers/plans/2026-09-25-harness-autonomy-phase3.md`, which shipped DAG
`approval` nodes on the rule "`default_option` must be a `stop` option" (spec §3.1, confirmed with the
user as a hard v1 constraint — see phase3 §9: "A *proceed* default is an unapproved action"). This
spec is the design fork that constraint deliberately deferred: a `proceed` default becomes legal, but
only under a condition Phase 3 didn't have machinery for — every side effect downstream is undoable.
**Decision:** `695c356d` (Tim approved 2026-09-26) — see also sibling decisions `671ee116` (reasoning
maps) and `28f021a0` (fault detector) approved in the same batch; this spec covers only the P2.8
stream. Rationale recorded in `695c356d`: ship compensation + proceed-default as a first increment
behind default-OFF flags, on an isolated branch/worktree, as a PR with no merge — Tier C (Opus, high
effort, advisor protocol) because it is harness/security-adjacent and has a real design fork (how a
free-form subtask declares undoability).
**Anchors from `main` at `8ecb396`** (Phases 1–3 of the roadmap merged: PRs #646–#650, #655, #658).
**Status note:** an implementation of this design was built and iterated as PR #652 ("compensation
registry") against an isolated worktree, closing four rounds of Codex findings. This document is the
standing design reference for that stream — written from a clean branch off `main`, no code, no PR
merge — so the architecture, the compensable-surface decision (Option A) and the flags are recorded
independently of any one PR's lifecycle. Where this spec differs from a claim in the roadmap's gap
analysis (§2 row P2.8), the roadmap is describing the *pre-P2.8* state; this document describes the
target design.

## 1. Goal

Two related capabilities, gated independently:

1. **Undo.** A background mutation (write_file, a schedule/heartbeat config change, a decision
   resolution, a CryptoTrader config change) can be reverted from a companion card, because the
   harness captured what it overwrote *before* it overwrote it.
2. **Reversible-default approval.** A DAG `approval` node — which today (Phase 3) may only default to
   a *stop* option — may default to `proceed` when, and only when, every side effect reachable behind
   it is compensable. This is validated structurally at `dag_create`, not hoped for at runtime.

Both capabilities are additive and default OFF. Turning them on does not change any existing
behavior until an operator (agent or DAG author) opts a specific node or approval into it.

## 2. Why this is two problems, not one

Phase 2a (`docs/superpowers/plans/2026-09-24-harness-autonomy-phase2a.md`) already gives every tool a
static risk class — `TOOL_CLASSES: Mapping[str, ToolClass]` in `nous/api/tool_classes.py`, each entry
a `side_effect` level (`none < write < external < irreversible`) plus a `spawns: bool`. That table
answers "how risky is this tool, in general" for the ActionGate tier, the ledger's classification and
the F078 refuse denylist, all of which read `TOOL_CLASSES` at import time.

Compensability is a different, narrower question: "if this *specific successful call* happened, can
we undo *its* effect." It doesn't fit on `ToolClass` as another risk level because:

- **`tool_classes.py` is a leaf module with no `nous`-internal imports** — the claim verifier,
  ActionGate and the ledger all read it at import time, before the app or DB is wired up. A
  compensator function needs the database and domain objects (the `Heart`/`Brain` stores, the
  scheduler, the CT config client) and must be registered at runtime, the same way tool handlers are.
- **Compensability is sometimes per-call, not per-tool.** `heartbeat_check_manage` is compensable only
  when its `action` argument is `"disable"` (re-enabling undoes it); `enable`/`update`/`delete`
  re-arm or rewrite a check's *future* runs, which is not something "undo" can mean.
- **A tool being low-risk (`write`) does not imply it is undoable**, and a tool with an `external` or
  `irreversible` class can still be flagged in the auto-review flow (§6) even with nothing to revert —
  the review card and the revert button are separable.

So: `ToolClass` keeps answering "how risky." A new, separate registry answers "can this call be
undone, and how." `TOOL_CLASSES` gains one new boolean field (`compensable: bool = False`) that flags
*membership* in the compensable set; the *mechanism* to undo a call lives in the new registry below.

## 3. The 2a risk-tag shape, extended: `register(name, compensate=fn)`

### 3.1 `ToolClass.compensable`

```
@dataclass(frozen=True)
class ToolClass:
    side_effect: SideEffect          # existing (2a): none | write | external | irreversible
    spawns: bool = False             # existing (2a)
    compensable: bool = False        # NEW: this tool CAN have a registered compensator
```

`compensable=True` is a static, per-tool declaration — it says "this tool's effect is the *kind* of
thing that can be undone," not "every call to it will be." The per-call refinement (the
`heartbeat_check_manage` case) is a separate predicate, `is_compensable_call(name, tool_input) ->
bool`, consulted wherever `TOOL_CLASSES[name].compensable` is checked; it defaults to "match the class
flag" for every tool except the ones that need the narrower per-call gate.

v1 compensable set: `write_file`, `resolve_decision`, `heartbeat_check_manage` (per-call: `disable`
only). See §4 for why `schedule_task` and `heartbeat_check_create` are explicitly *not* in this set,
despite superficially looking undoable.

### 3.2 `nous/api/compensation.py` (new leaf-adjacent module)

A new module, separate from `tool_classes.py` for the reasons in §2, holding:

- `CompensationResult` — outcome of a revert attempt: `status: Literal["success", "already_reverted",
  "failed"]`, plus a human-readable `detail` string for the surface.
- `CompensatorFn = Callable[[ledger_entry_id: str, snapshot_data: dict], Awaitable[CompensationResult]]`
- `CompensationRegistry` — `register(tool_name: str, compensator: CompensatorFn) -> None`,
  `get(tool_name: str) -> CompensatorFn | None`, `is_compensable(tool_name: str) -> bool` (consults
  `TOOL_CLASSES[tool_name].compensable`, the source of truth — the registry does not duplicate that
  flag, it only holds the *function*). Registered once at process startup (`nous/main.py`), not at
  import time, because compensators close over the database session factory and domain services.
- The four built-in compensators (§5): `compensate_write_file`, `compensate_heartbeat_check_manage`,
  `compensate_resolve_decision`, and the CT-config compensator (§5.4).

### 3.3 `register(..., compensate=fn)` — the call-site shape asked for in this spec

The registration call the agent-facing description of this feature uses (`register(tool_name,
compensate=fn)`) maps directly onto `CompensationRegistry.register(tool_name, compensator)` above —
`compensate=` is the keyword name at the call site, matching the vocabulary used when this stream was
scoped (decision `695c356d`). Each of the four built-ins is one `register("write_file",
compensate=compensate_write_file)`-shaped call in the startup wiring; there is exactly one call site
per compensable tool, so an AST-level drift test (mirroring the one Phase 2a already runs against
`TOOL_CLASSES`) can assert that every tool marked `compensable=True` has exactly one registration and
vice versa — a class flag with no registered function, or a registration for a tool not marked
compensable, both fail the test.

## 4. Compensation snapshots — captured *before* the call, not reconstructed after

A revert can only restore what was actually there before. The runner captures a **snapshot** of the
state a compensable call is about to change, immediately before dispatch, whenever that call runs in
a background context (subtask, DAG node, scheduled task, heartbeat check/callback) — regardless of
whether the enclosing DAG node is marked `undoable` (§7). `undoable` decides whether a snapshot that
*cannot* be taken (e.g. an oversized file) blocks the call outright; it does not decide whether a
snapshot is captured for an otherwise-normal background mutation. This closes the gap the roadmap's
gap analysis calls out at §2 row P2.8 and mirrors the Phase 2a principle of "declare once, enforce at
the real choke point" rather than trusting each call site to remember.

**Storage:** a new table, `nous_system.compensation_snapshots` (new migration in the `077+` series —
renumber against whatever the next free migration id is at merge time), keyed by `ledger_entry_id`
(the P1.4/1b execution-ledger row this call already produces), holding: `tool_name`, `snapshot_data`
(JSONB — the prior state, tool-specific shape below), `captured_at`, `reverted_at` (nullable — set
once, never cleared; this is what makes `review.revert` idempotent, §6), `revert_status`.

No secrets, no full request/response bodies beyond what each compensator specifically needs to
restore state (a file's prior bytes, a decision's prior outcome/resolution_note, a check's prior
enabled bit, a CT config's prior parameter values) — the same "no bodies, no secrets" discipline the
roadmap already applies to the 1b execution ledger.

## 5. The four compensators

| Tool | Snapshot | Compensator behavior |
|---|---|---|
| `write_file` | Prior file content (or a marker that the file did not exist) | Restore prior content; if the file was new, delete it on revert |
| `schedule_task` / `heartbeat_check_create` config change | *(not compensable — see below)* | — |
| `heartbeat_check_manage` (`action="disable"` only) | Check name (the check's other config is untouched by a disable) | Re-enable the check |
| `resolve_decision` | Prior outcome + prior resolution_note (state immediately before this resolve) | Write the prior outcome/resolution_note back onto the decision row |
| CryptoTrader config change (`autopilot`/CT parameter proposals applied through the CT client) | Prior parameter values for every field the proposal touched | Re-apply the prior parameter values through the same CT config-write path used to apply the original change |

### 5.1 `write_file`

Read-before-write: capture prior bytes (or "did not exist") before the write lands. Revert restores
the prior bytes, or deletes the file if the snapshot says it was newly created. If the underlying file
was deleted out-of-band before a revert is attempted, the compensator reports `failed` with a clear
`detail` rather than silently no-op'ing — a silent no-op reads as "reverted" when nothing happened.

### 5.2 Schedule / heartbeat check changes — narrowed on purpose (Option A)

The obvious design is "cancel the schedule / disable the check on revert." That is *unsound* for the
creation case and this spec deliberately narrows the compensable surface rather than shipping a false
promise:

- `schedule_task`: a schedule set for "in 0 minutes" (or any interval shorter than the time a person
  has to notice and hit Revert) starts a subtask immediately. `TaskScheduler._fire_due_tasks()` has
  already run and spawned real work by the time anyone could revert. Cancelling the *schedule* after
  the fact does not undo the *subtask it started*.
- `heartbeat_check_create`: a newly created dynamic check can be immediately due and run `bash` (or
  any tool in its declared tool list) before a revert path exists. Same problem: "undo" can only mean
  "turn the check off going forward," which is not what compensation promises.

So: **`schedule_task` and `heartbeat_check_create` are explicitly NOT in the compensable set.** They
stay in the `_SPAWN` class from Phase 2a (`spawns=True`), with `compensable=False`. On a DAG node
declared `undoable` (§7), calling either of these fails closed with a `not_compensable` violation —
the same enforcement path as any other non-compensable call on an undoable node, not a special case.

`heartbeat_check_manage`, in contrast, *modifies* an existing check rather than spawning new
immediate work — and only its `disable` action is genuinely reversible (re-enabling puts the check
back exactly where it was). `enable` / `update` / `delete` all re-arm or rewrite a check's *future*
runs and are excluded via the per-call gate `is_compensable_call("heartbeat_check_manage",
tool_input)` (§3.1), not the class flag — the class stays `compensable=True` so its compensator can be
registered at all, and the per-call predicate does the narrowing at dispatch time.

**Design principle this establishes:** compensability is judged by "can we undo the *effect that
already happened*," never by "can we prevent effects that haven't happened yet." A tool that spawns
irreversible follow-on work is not made compensable by being able to stop *future* instances of that
work.

### 5.3 `resolve_decision`

Snapshot the outcome/resolution_note immediately before the resolve call executes; revert writes that
prior state back. This is a pure metadata rewrite with no spawned side effects, so it is compensable
without the narrowing §5.2 required.

### 5.4 CryptoTrader config changes

CT parameter changes (entry_threshold, exit_threshold, position sizing, etc.) applied through the
existing CT config-write path are snapshotted the same way as any other compensable call: capture the
full set of prior parameter values for every field the proposal touches, before the write lands.
Revert re-applies those prior values through the identical write path used for the original change —
not a bespoke rollback route — so the same validation, cooldown and audit trail that gates a normal CT
config change also gates its reversal. **Explicit exclusion carried over from existing CT censors:**
a revert must never be used to route around the standing rule against tightening `exit_threshold` to
force-close an underwater position (see the live `exit_threshold` censor) — the compensator restores
prior *values*, it does not re-run CT's own safety gates in a mode that could sidestep them; if a
proposed revert would violate a live censor, the censor fires exactly as it would on any other CT
config write attempting the same value.

## 6. `review.revert` — resolving an `execution_ledger` row to its compensator

A new action handler, `review.revert`, registered on the existing `ActionRouter` (the same dispatcher
`review.approve`/`review.reject`-style handlers already use). Given a `trace_id` from the action
context (the id already threading through every `action_review` card):

1. Resolve `trace_id` → `ledger_entry_id` (the execution-ledger row this call produced — P1.4/1b).
2. Look up the compensation snapshot for that `ledger_entry_id` in `compensation_snapshots`.
3. Look up the tool's compensator from `CompensationRegistry.get(tool_name)`.
4. Call the compensator with `(ledger_entry_id, snapshot_data)`.
5. Record the result (`success` / `already_reverted` / `failed`) — the write to `reverted_at` is a
   conditional `UPDATE ... WHERE reverted_at IS NULL`, the same idempotency pattern Phase 3 uses for
   its own conditional node transitions (`DAGStore.transition_node`), so a double-tap or a retried
   action resolves to `already_reverted` rather than reverting twice.
6. Update the surface to show the revert status (success / already-reverted / failed-with-detail).

**Security, reusing an existing invariant:** the card only offers a Revert button when
`compensation.revertible=True` AND `compensation.handler` is set (§7 of the roadmap's gap table
already names `compensation.handler` as "free text never read" — this spec is what starts reading it).
A forged `review.revert` action posted against a card that never offered it is rejected at the
existing allowlist check (the same test class the harness already runs against forged actions on
non-offering cards). The handler additionally refuses any request with no real `ledger_entry_id` / no
snapshot row — "no snapshot" means "nothing to revert," never "assume success."

Compensation **restores, never deletes** — a revert always writes the prior state back; it never
simply removes the row or the effect, so the system's history stays legible (what happened, then what
was reverted, both visible) rather than looking as if the original action never occurred.

## 7. Auto `action_review` for background external/irreversible calls

Today, nothing pushes a review card automatically after a background mutating call — a person only
sees one if the agent chooses to `push_surface(template="action_review", ...)` by hand. This spec
adds an automatic push, gated by its own flag (§9), for calls in background contexts that are
`external` or `irreversible` per Phase 2a's `TOOL_CLASSES`, or that are `compensable` (so there is
something to revert even if the underlying risk level is only `write`). The pushed card carries the
existing `action_review` shape (`did`, `why`, `cost`, `compensation={revertible, handler, note}`,
`trace_id`) with `compensation.revertible` and `compensation.handler` populated for real when a
compensator exists — closing the gap-table's "no revert executor" finding end to end: register →
snapshot → card offers Revert → `review.revert` resolves it.

v1 scope is background contexts only (subtask, DAG node, scheduled task, heartbeat check/callback);
interactive-turn auto-review is deliberately deferred (§10) because a person watching the turn happen
already has the chance to object in real time, which is the gap this mechanism exists to close for
*unattended* work specifically.

## 8. Reversible-default approval nodes — relaxing Phase 3's `default_option` rule

Phase 3 shipped DAG `approval` nodes with one hard rule (spec §3.1, confirmed with the user): every
`default_option` must be a `stop` option, because "a *proceed* default is an unapproved action." This
spec adds the one condition under which that concern is actually addressed rather than waved away:
**`default_option` may be `'proceed'` only when every side effect reachable behind the acting node is
compensable — validated structurally at `dag_create`, before the DAG ever runs.**

### 8.1 The free-form-subtask problem, and the `undoable` field

A `subtask`/DAG-node turn runs a free-form LLM turn with access to whatever tools it's offered.
`dag_create` cannot know in advance which tools that turn will actually call — so it cannot prove
compensability by inspecting the node's spec alone. The resolution: an explicit `undoable: bool =
False` field on `DAGNodeSpec` that the DAG's author sets. `undoable: true` is a **declaration with
runtime teeth**, not just a label:

- **At `dag_create` (structural validation):** an approval node's `default_option` may be `'proceed'`
  only if every successor reachable from it via `dependency`/`context_flow` edges is either (a) a
  non-side-effecting node type (`gate`, `check` with no mutating tool list) or (b) a `subtask`/DAG-node
  explicitly marked `undoable: true`. Any successor that is an ordinary node (not marked `undoable`)
  fails DAG creation outright — the same place Phase 3 already validates that every `default_option`
  is legal (its own §3.1 check; this spec extends that same validator rather than adding a second one,
  matching the roadmap's stated preference for one choke point over parallel enforcement paths).
- **At dispatch time (runtime enforcement):** every tool call from an `undoable`-flagged node is
  checked against `CompensationRegistry.is_compensable(tool_name)` / `is_compensable_call(...)`
  (§3.1) at the same choke point Phase 2a's `tool_policy.evaluate` already occupies. A call to a
  non-compensable tool from an `undoable` node is refused with a `not_compensable` violation — hard
  refusal, not a warn-and-continue, and not contingent on `NOUS_TOOL_CONTEXT_POLICY_MODE` (declaring a
  node `undoable` is itself an opt-in to the stricter mode for that node, independent of the global
  policy-mode setting).

This closes the loop the naive design would leave open: "declare it undoable" is worthless if nothing
stops the node from calling `send_email` anyway. The declaration is enforced, not trusted.

### 8.2 Threading `undoable` through to enforcement

`DAGNodeSpec.undoable` → `dag_nodes` (persisted column) → subtask metadata (passed when the node's
subtask/turn is launched) → `ExecutionContext.undoable: bool` (read at the tool-dispatch choke point)
→ `tool_policy.evaluate` (new `not_compensable` violation type, alongside Phase 2a's existing
violation vocabulary). No new choke point is added; the existing per-call authorization path gains one
more condition to check, the same shape as every other Phase 2a policy row.

### 8.3 What "every side effect is compensable" does NOT cover

- A `completion_check` (a raw shell command Phase 3's `check`/subtask nodes can poll with) runs
  outside tool authorization entirely — it is not a tool call, so `tool_policy.evaluate` never sees
  it and cannot snapshot or refuse it. An approval node whose downstream includes any node declaring a
  `completion_check` cannot legally default to `proceed`, regardless of the `undoable` flags on its
  tool calls — the validator in §8.1 must reject this combination explicitly, not just check the tool
  list.
- `bash` / `run_python` are not given blanket compensators (§10) — a node that calls either while
  marked `undoable` will have that specific call refused at dispatch (§8.1's runtime enforcement),
  which in practice means an `undoable` node's tool offering should exclude `bash`/`run_python` if the
  author wants the node to actually be able to do anything, or accept that those calls will be
  blocked mid-turn.
- A person tapping `proceed` explicitly (rather than the deadline firing the default) is never
  affected by any of this — §8 only changes what happens when **nobody answers** and the deadline
  applies the node's own default. An explicit human `proceed` tap was never the problem Phase 3's
  hard rule was guarding against.

## 9. Flags — all OFF by default

| Setting | Default | Gates | Depends on |
|---|---|---|---|
| `NOUS_COMPENSATION_ENABLED` | `false` | Master switch: registry active, snapshots captured, compensators registered. When `false`, no snapshots are taken and an `undoable` node refuses any call it cannot snapshot, and any non-compensable side effect, regardless of `NOUS_TOOL_CONTEXT_POLICY_MODE`. | `NOUS_EXECUTION_LEDGER_PERSIST_ENABLED` (snapshots are keyed by ledger row, P1.4/1b) |
| `NOUS_COMPENSATION_AUTO_REVIEW_ENABLED` | `false` | Auto-push an `action_review` surface after a qualifying background mutation (§7). | `NOUS_COMPENSATION_ENABLED` |
| `NOUS_DAG_APPROVAL_PROCEED_DEFAULT_ENABLED` | `false` | Allow `dag_create` to accept a `'proceed'` `default_option` when every downstream side effect is declared `undoable` and none declares a `completion_check` (§8.3). | `NOUS_COMPENSATION_ENABLED` AND `NOUS_COMPENSATION_AUTO_REVIEW_ENABLED` — the auto-review card is the person's only surface for noticing and reverting a background mutation that proceeded without them, so proceed-default is meaningless without it also being reviewable |

Turning all three on is required before any DAG can actually exercise a `proceed` default in
practice; each flag alone is inert. This mirrors the roadmap's general rollout pattern (Phase 1's `1b`
ledger, Phase 2a's `warn`-first context policy): land the machinery dark, verify via the ledger/events
it produces, then flip flags one at a time with real production evidence between each flip — not as a
single atomic switch.

## 10. Deliberately deferred (out of scope for this increment)

- Compensators for `learn_fact`, `record_decision` (create), `create_censor` — these touch the
  knowledge graph / admission side effects, where "undo" is not a clean state restore (edges,
  activation weights and downstream inferences may already depend on the new node).
- General-purpose compensators for `bash` / `run_python` — no sound way to undo an arbitrary
  command/script; an `undoable` node that calls either is refused at dispatch (§8.3), not given a
  fabricated compensator.
- Auto `action_review` for interactive (non-background) turns — a person watching the turn happen
  already has the chance to object live.
- Compensation cost tracking / budget accounting for revert operations.
- A UI for browsing compensation history beyond the per-card Revert button (e.g. a searchable ledger
  of past reverts) — the harness dashboard (`docs/superpowers/specs/2026-09-25-harness-dashboard-visibility-design.md`)
  is the natural home for this if it's wanted later.

## 11. Test surface (names only — no code in this document)

- Registry: register/get/is_compensable round-trip; a tool flagged `compensable=True` with no
  registered compensator fails the drift test (§3.3); a registered compensator for a tool not flagged
  compensable also fails it.
- Snapshots: capture creates a row; `mark_reverted` is idempotent (double-revert is a no-op that
  reports `already_reverted`, never a second mutation).
- Each of the four compensators: happy path (restore), already-reverted path, and a failure path
  (e.g. `write_file`'s target deleted out-of-band before revert; CT config write rejected by a live
  censor on re-apply).
- `review.revert`: forged action on a non-revertible card rejected at the allowlist (existing
  invariant, re-asserted); real revert on a revertible card succeeds and idempotently no-ops on retry.
- Proceed-default validator: rejected when the flag is off; rejected when any downstream node isn't
  `undoable`; rejected when any downstream node declares a `completion_check`; accepted only when the
  flag is on AND every downstream side-effecting node is `undoable` AND none has a `completion_check`.
- Runtime enforcement: a non-compensable tool call from an `undoable` node is refused with
  `not_compensable`, independent of `NOUS_TOOL_CONTEXT_POLICY_MODE`.
- `schedule_task` / `heartbeat_check_create` explicitly assert `compensable=False` and are refused on
  an `undoable` node (regression guard against Option A silently regressing to the naive design in §5.2).

## 12. Rollout

1. Ship all three flags OFF. Registry, snapshots and the `review.revert` handler are live but inert
   (no snapshots captured, no cards auto-pushed, no proceed-default DAGs can validate).
2. Flip `NOUS_COMPENSATION_ENABLED` first; observe snapshot volume and compensator failure rate via
   the execution ledger for a full week before touching the next flag.
3. Flip `NOUS_COMPENSATION_AUTO_REVIEW_ENABLED`; watch real Revert usage on real cards.
4. Flip `NOUS_DAG_APPROVAL_PROCEED_DEFAULT_ENABLED` last, and only after 2–3 is providing real
   evidence that reverts work reliably in practice — widening what "silent consent" is allowed to do
   is the highest-stakes step in this spec and should be the most evidence-gated one.
