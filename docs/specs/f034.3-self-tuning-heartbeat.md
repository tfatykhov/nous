# F034.3 — Self-Tuning Heartbeat

**Status:** PROPOSED  
**Priority:** P3 (long-term, aspirational)  
**Depends on:** F034.1 Finding Lifecycle (required), F034.2 Intelligent Checks (recommended)  
**Author:** Nous + Tim  
**Date:** 2026-04-03  

## Problem

Heartbeat checks have fixed thresholds and static urgency classifications. A HealthCheck
that surfaces stale facts every day but Tim never acts on them wastes attention and tokens.
An EmailCheck that classifies newsletters as "actionable" keeps being wrong. The system
doesn't learn from outcomes.

The heartbeat should **adapt to what Tim actually cares about** — learning from finding 
outcomes to tune its own behavior over time.

## Core Concept

Apply the EvoSkill pattern (effectiveness tracking → parameter adjustment) to heartbeat 
checks. Every finding has an outcome. Outcomes drive threshold and urgency adjustments.

```
Finding → Triage → Action/Dismiss → Outcome Signal → Parameter Update
```

## Design

### 3.1 Outcome Signals

Each finding's lifecycle (from F034.1) produces an outcome signal:

| Outcome | Signal | Meaning |
|---------|--------|---------|
| Tim acts on finding within 1 hour | `strong_positive` | This was important and urgent |
| Tim acts on finding within 24 hours | `positive` | This was worth surfacing |
| Finding acknowledged, no action in 72h | `weak_negative` | Probably not worth the attention |
| Finding suppressed 3+ times before action | `negative` | Too noisy, threshold too sensitive |
| Tim manually resolves via REST API | `positive` | Cared enough to interact |
| Finding escalated before action | `neutral` | Unclear — needed prompting? |
| Tim explicitly dismisses | `strong_negative` | Wrong signal entirely |

"Tim acts on finding" is detected by:
- A cognitive session that modifies facts/decisions/censors related to the finding topic
- Tim sends a message referencing the finding topic within the time window
- The underlying condition resolves (e.g., stale decisions get reviewed)

### 3.2 Tunable Parameters

Each check exposes parameters that the tuning engine can adjust:

**HealthCheck:**
- `stale_decision_days`: default 7, range [3, 30]
- `stale_fact_days`: default 30, range [7, 90]
- `low_effectiveness_threshold`: default 0.5, range [0.3, 0.8]
- `max_findings_per_run`: default 10, range [3, 25]

**SelfInitiatedCheck:**
- `similarity_threshold`: default 0.75, range [0.6, 0.9]
- `lookback_days`: default 14, range [3, 30]
- `max_pending_items`: default 5, range [2, 15]

**EmailCheck:**
- `sender_reputation_weight`: default 0.5, range [0.0, 1.0]
- `llm_classification_budget`: default 500 tokens, range [200, 2000]

**DriveCheck:**
- `significance_threshold`: default "normal", options [low, normal, high]
- `cross_reference_lookback_hours`: default 48, range [6, 168]

**Global:**
- `escalation_hours_normal_to_high`: default 24, range [6, 72]
- `escalation_hours_low_to_normal`: default 72, range [24, 168]
- `daily_token_budget`: default 50000, range [10000, 200000]

### 3.3 Tuning Engine

The tuning engine runs periodically (default: weekly, configurable) and adjusts 
parameters based on accumulated outcome signals.

```python
class HeartbeatTuner:
    """Adjusts check parameters based on finding outcome history."""
    
    LEARNING_RATE = 0.1  # Conservative — small adjustments
    MIN_SAMPLES = 10     # Need enough data before adjusting
    
    async def tune(self, finding_store: FindingStore, check_registry: CheckRegistry):
        """Run a tuning pass over all checks."""
        for check in check_registry.all_checks():
            outcomes = finding_store.get_outcomes_for_check(
                check.name, since=timedelta(days=30)
            )
            
            if len(outcomes) < self.MIN_SAMPLES:
                continue  # Not enough data
            
            adjustments = self._compute_adjustments(check, outcomes)
            
            for param, direction in adjustments.items():
                current = check.get_param(param)
                meta = check.get_param_meta(param)  # min, max, step
                
                if direction == "relax":
                    # Too many negatives — make check less sensitive
                    new_value = min(current + meta.step, meta.max)
                elif direction == "tighten":
                    # Too many positives being missed — make check more sensitive
                    new_value = max(current - meta.step, meta.min)
                else:
                    continue
                
                check.set_param(param, new_value)
                
                # Record the adjustment as a decision
                await self._record_tuning_decision(check, param, current, new_value, outcomes)
    
    def _compute_adjustments(self, check, outcomes) -> dict[str, str]:
        """Determine which parameters to relax or tighten."""
        positive_rate = sum(1 for o in outcomes if o.signal in 
                          ("strong_positive", "positive")) / len(outcomes)
        negative_rate = sum(1 for o in outcomes if o.signal in 
                          ("strong_negative", "negative")) / len(outcomes)
        
        adjustments = {}
        
        if negative_rate > 0.6:
            # More than 60% of findings are noise — relax thresholds
            for param in check.tunable_params():
                adjustments[param] = "relax"
        
        elif positive_rate > 0.8:
            # Almost everything surfaced is useful — could we catch more?
            # Tighten (lower) thresholds to surface more findings
            for param in check.tunable_params():
                adjustments[param] = "tighten"
        
        return adjustments
```

### 3.4 Guardrails

Self-tuning must be safe:

- **Parameter bounds** — Every tunable param has hard min/max. The tuner cannot exceed them.
- **Learning rate** — Small steps only. No single tuning pass can change a parameter by 
  more than 10% of its range.
- **Minimum samples** — Won't adjust until 10+ outcome signals collected. Prevents 
  overreaction to small samples.
- **Decision recording** — Every adjustment is recorded as a Brain decision with the 
  outcome data that drove it. Full audit trail.
- **Manual override** — Parameters set via REST API are pinned and won't be auto-tuned 
  until unpinned. Tim always has final say.
- **Rollback** — If post-adjustment negative rate increases by >20%, auto-rollback to 
  previous values and record the failed experiment.

### 3.5 Tuning Report

After each tuning pass, generate a summary (stored as fact, optionally sent to Telegram):

```
🔧 Heartbeat Tuning Report (2026-04-10)

HealthCheck:
  • stale_decision_days: 7 → 10 (relaxed — 70% of stale decision findings were ignored)
  • stale_fact_days: 30 → 30 (no change — balanced outcome distribution)

EmailCheck:
  • sender_reputation_weight: 0.5 → 0.6 (tightened — reputation-based classification 
    is proving accurate)

SelfInitiatedCheck:
  • similarity_threshold: 0.75 → 0.72 (tightened — catching more real pending items)

No changes: DriveCheck (insufficient data — 4 outcomes, need 10)
```

### 3.6 The Virtuous Cycle

Over weeks/months, this creates a feedback loop:

1. Checks surface findings
2. Findings get triaged and acted on (or not)
3. Outcomes accumulate
4. Tuner adjusts parameters
5. Checks become more aligned with what Tim cares about
6. Less noise → more trust → Tim engages more → better outcome signals
7. → Repeat

This is the same principle behind EvoSkill (procedure effectiveness tracking) but applied 
to the heartbeat's self-monitoring behavior. The heartbeat literally learns what's worth 
paying attention to.

### 3.7 Future: Per-Finding-Type Tuning

Phase 2 ambition: Don't just tune check-level parameters — tune per finding *type*.

Example: HealthCheck surfaces both "stale decisions" and "low effectiveness procedures." 
Tim always acts on stale decisions but ignores low effectiveness findings. The tuner 
should learn to:
- Keep surfacing stale decisions (positive signal)
- Reduce urgency of low-effectiveness findings (negative signal)
- Without changing the HealthCheck's overall sensitivity

This requires finding categorization within each check — tagging findings with a 
`finding_type` that the tuner can track independently.

## Risks

- **Reward hacking** — Tuner could learn to suppress everything (100% negative → relax 
  all thresholds to max → no findings → no negatives). Mitigated by minimum sensitivity 
  floors and the "tighten on high positive rate" logic.
- **Slow learning** — Weekly tuning with 10-sample minimum means ~2 months before 
  meaningful adaptation. Acceptable for a v1; can accelerate later.
- **Outcome attribution** — "Tim acted on this" is inferred, not explicit. Could 
  misattribute. Mitigated by conservative learning rate — noisy signals get averaged out.
