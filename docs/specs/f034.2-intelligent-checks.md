# F034.2 — Intelligent Checks

**Status:** PROPOSED  
**Priority:** P2 (medium-term)  
**Depends on:** F034 Heartbeat (merged), F034.1 Finding Lifecycle (recommended)  
**Author:** Nous + Tim  
**Date:** 2026-04-03  

## Problem

The four heartbeat checks in F034 use basic heuristics: substring matching for TODOs,
keyword lists for email urgency, raw file modification timestamps for Drive. These
produce noisy, low-context findings. The checks need to graduate from **pattern matching
to understanding**.

## Scope

Three independent improvements, implementable in any order:

1. **SelfInitiatedCheck** — keyword grep → semantic intent matching
2. **EmailCheck** — keyword urgency → LLM classification with graceful degradation
3. **DriveCheck** — raw modification alerts → contextual change awareness

---

## 1. Smart SelfInitiatedCheck

### Current Behavior
Searches facts for substrings: "TODO", "follow-up", "action item", "pending".
Misses implicit commitments and contextual urgency.

### Target Behavior

**1a. Embedding-based pending action detection**

Define a set of prototype embeddings for "pending action" concepts:
```python
PENDING_PROTOTYPES = [
    "I need to follow up on this",
    "This task is waiting for completion", 
    "Tim asked me to do this and I haven't yet",
    "This should be revisited soon",
    "Action required but not yet taken",
]
```

At check time:
- Embed the prototypes (cached, done once)
- Run a cosine similarity search against recent facts (last 14 days)
- Facts with similarity > 0.75 to any prototype = candidate pending actions
- Filter out facts already linked to completed episodes or resolved findings

This catches things like "Tim mentioned he'd want a comparison doc by Friday" without
needing the word "TODO" anywhere.

**1b. Conversation promise tracking**

Scan recent episode summaries for patterns indicating unresolved commitments:
- "I'll look into..." / "Let me research..." / "I'll draft..."
- Any episode with `outcome: ongoing` that's older than 48 hours
- Episodes where the structured_summary contains action items not linked to 
  subsequent completed episodes

Implementation: A lightweight pass over recent episode summaries using the same
embedding approach (prototype = "unfinished commitment").

**1c. Temporal awareness**

Some facts and findings have implicit deadlines:
- "Tim said he'd decide by end of week" → surface on Thursday
- "Quarterly review is next month" → surface 1 week before
- "This PR has been open for 3 days" → escalate based on team norms

Phase 1: Parse explicit temporal markers (dates, "by Friday", "next week") from 
fact content. Use dateutil/dateparser for fuzzy parsing.

Phase 2: Use LLM to infer implicit deadlines from context.

### Estimated Effort
- Embedding prototype matching: ~100 lines + tests
- Promise tracking: ~80 lines + tests  
- Temporal awareness (Phase 1): ~60 lines + tests

## 2. LLM-Powered Email Classification

### Current Behavior
Checks email subject for keywords: "urgent", "critical", "down", "alert", "emergency".
High false-positive rate (marketing emails) and false-negative rate (contextually urgent
emails without alarm words).

### Target Behavior

**2a. Tiered classification with budget awareness**

```python
async def classify_email(self, subject: str, body_preview: str) -> EmailClassification:
    # Tier 1: Keyword heuristics (free, always available)
    keyword_result = self._keyword_classify(subject)
    
    # Tier 2: LLM classification (costs tokens, budget-gated)
    if self._token_budget_available(estimated_cost=500):
        llm_result = await self._llm_classify(subject, body_preview[:200])
        return llm_result  # More accurate
    
    return keyword_result  # Graceful degradation
```

**LLM classification prompt** (compact, ~200 input tokens):
```
Classify this email. Reply with ONE word: urgent, actionable, informational, spam.

From: {sender}
Subject: {subject}
Preview: {body_preview[:200]}
```

**2b. Sender reputation learning**

Over time, build a sender → typical_classification mapping:
- If sender X has sent 10 emails all classified as "informational", auto-classify 
  future emails from X as "informational" without LLM call
- Stored as Heart facts: "Email sender noreply@github.com typically sends: actionable"
- Reputation decays over 30 days (sender behavior can change)
- New/unknown senders always get LLM classification

**2c. Integration with F034.1**

Email findings use message_id as part of the fingerprint. The existing `_seen_ids` 
mechanism in EmailCheck is replaced by the FindingStore from F034.1 — unified lifecycle
management instead of a separate dedup system per check.

### Estimated Effort
- Tiered classification: ~80 lines + tests
- Sender reputation: ~100 lines + tests
- Budget integration: ~30 lines

## 3. Contextual DriveCheck

### Current Behavior
Polls Google Drive API for files modified since last check. Reports filename + 
modification time. No context about why the change matters.

### Target Behavior

**3a. Project folder mapping**

Maintain a configurable mapping of Drive folders to projects:
```python
# Stored as Heart facts or config
FOLDER_MAP = {
    "nous-specs/": "nous",
    "articles/": "writing", 
    "verdicto/": "verdicto",
    "shared-with-me/": "external",
}
```

Findings include project context:
```
"Q2-roadmap.docx modified in nous-specs/ (project: nous)"
```

**3b. Change significance scoring**

Not all modifications are equal. Score by:
- **New file** in a known project folder → high significance
- **File shared by someone else** → high (external input)
- **Edit to existing file by Tim** → normal
- **Auto-save / minor edit** (small delta, same day as creation) → low
- **File in unknown folder** → low (probably not project-related)

Use Google Drive API revision history to determine change magnitude.

**3c. Conversation cross-reference**

When a Drive file is modified:
1. Search recent episodes for mentions of the filename or related keywords
2. If found: "Q2-roadmap.docx was modified — you discussed this 2 hours ago"
3. This makes the finding contextually relevant, not just a raw notification

```python
async def _contextualize(self, file_name: str, file_id: str) -> str | None:
    """Search recent conversations for references to this file."""
    results = await self.recall_deep(file_name, limit=3)
    if results and results[0].score > 0.7:
        episode = results[0]
        return f"Related to recent conversation: {episode.summary[:100]}"
    return None
```

**3d. Content-aware summaries (Phase 2)**

For Google Docs/Sheets, use the Drive API to fetch content diff:
- Docs: Compare current vs previous revision, summarize changes
- Sheets: Detect new rows/columns, formula changes
- This is expensive (API calls + LLM summarization) so gated behind token budget

### Estimated Effort
- Folder mapping + significance scoring: ~120 lines + tests
- Conversation cross-reference: ~60 lines + tests
- Content-aware summaries: ~150 lines + tests (Phase 2)

## Implementation Order

Recommended sequence within this spec:

1. **SelfInitiatedCheck 1a** (embedding prototypes) — Highest value, most findings improved
2. **EmailCheck 2a** (tiered classification) — Quick win, already has infrastructure
3. **DriveCheck 3a+3b** (folder mapping + significance) — Config-driven, no LLM needed
4. **SelfInitiatedCheck 1b** (promise tracking) — Builds on episode summary infrastructure
5. **EmailCheck 2b** (sender reputation) — Learning layer
6. **DriveCheck 3c** (conversation cross-reference) — Needs recall_deep integration
7. **SelfInitiatedCheck 1c** (temporal awareness) — Most complex, fuzzy date parsing
8. **DriveCheck 3d** (content summaries) — Expensive, do last

## Total Estimated Effort

~780 lines of implementation + ~600 lines of tests across all three checks.
