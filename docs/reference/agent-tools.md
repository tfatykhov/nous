# Agent Tools

Documented tools the agent can call, and the cognitive frames each is offered in; the `dispatcher.register()` calls are the full list. Part of the [Nous development guide](../../CLAUDE.md).

| Tool | Frame Access | Description |
|------|-------------|-------------|
| `record_decision` | decision, task, debug, conversation, question | Record a decision with confidence + reasoning |
| `recall_deep` | all | Search memory (decisions, facts, episodes) |
| `recall_recent` | all | Retrieve recent memory items |
| `learn_fact` | conversation, question, creative, task | Store a new fact |
| `learn_skill` | conversation, question, task | Register a skill from URL, local path, or inline markdown |
| `ingest_document` | conversation, question, task, debug | F069: chunk & persist a full document body (arxiv, PDF/.docx text, long markdown) to heart.episode_chunks with source_kind='document'. Use after extracting text yourself via run_python / web_fetch. |
| `get_procedure` | all | Retrieve a specific procedure by ID (a job-lesson id reads as not found) |
| `create_censor` | all | Create a guardrail censor |
| `resolve_decision` | conversation, question, decision, task | Record the outcome of one decision (`success`/`partial`/`failure`, or `noise`/`superseded`, which calibration skips). A background turn may apply only `noise` and `superseded`, never over a graded outcome. Not offered to a `heartbeat_triage` turn, and refused there in every mode (`tool_policy.heartbeat_resolve_violation`) |
| `resolve_decisions` | conversation, question, decision, task | Resolve a batch of decisions in one transaction; a failed item does not stop the batch. Same background and `heartbeat_triage` rules as `resolve_decision` |
| `cache_retrieve` | all | Retrieve the original of a SmartCompressed result (bash, web_search, web_fetch, dag_manage) by the `cache_retrieve key` its marker names. Optional `lines` ("A-B", "A–B" or "A", 1-based, inclusive) uses the numbers of the `[… result lines A–B omitted …]` markers and returns exactly those lines under a `[result lines A–B of N]` header; optional `query` filters (after the range, with both). One answer is capped at 30,000 chars, cut after the last whole line with a footer naming the `lines=` range for the rest. Its output is never compressed |
| `db_query` | conversation, question, decision, debug, task | Run one read-only `SELECT` or `WITH` statement and get the rows as compact text. Registered only when `NOUS_READER_DB_PASSWORD` is set and that login passes the reader check at start-up. Every call logs in as `nous_reader` (`scripts/ops/db_roles.sql`), whose grants PostgreSQL enforces: the columns of `brain.intentions`, `brain.intention_arrivals`, `brain.intention_proposals`, `brain.decisions`, `heart.subtasks`, `heart.schedules`, `heart.facts`, `heart.episodes`, `nous_system.execution_dags`, `nous_system.dag_nodes`, `nous_system.dag_edges`, `nous_system.dynamic_checks`, `nous_system.execution_ledger` and `nous_system.events`, without embeddings, search vectors, raw episode transcripts or lease tokens; nothing in `scoring`, no push tokens, no other table. A fresh connection per call (at most two at once) in a READ ONLY transaction, 5 s statement timeout, 7 s for the whole call; at most 200 rows, 64 columns, 500 characters per cell (cut on the server first) and 100,000 characters in all; every cell passes the ledger's secret redaction before the clip. Class read (`none`): offered to `internal_only` lineage turns too, and, like every read, not written to the durable execution ledger (one log line per call keeps a hash of the statement, never its text). Redaction masks known secret formats and this process's own secrets; an unlabeled secret pasted into a readable text column (an event's data, a ledger output, a proposal's arguments) is shown as stored. Like any login it sees catalog names and the statistics views, so `scoring`'s row counts and column names are visible, not the scores. A large generated set (such as `generate_series` in FROM, which is materialised whole) is refused by the reader's 256 MB temp-file limit |
| `bash` | task, debug, conversation, question | Execute shell commands. `timeout` is clamped to 1..300 s; omitted, it is 30 s in a short turn (`ExecutionContext.is_short_turn`: a chat or MCP turn, a companion action, a heartbeat check, a DAG summary, and a subtask, scheduled or DAG-node turn whose row's `timeout_seconds` is 120 s or less, such as an inline `spawn_sync`), and 120 s in every other background turn. With the default `NOUS_TOOL_TIMEOUT` of 120 s the runner's per-tool timeout ends such a call at the same moment and its generic error replaces the retry hint (prod runs 2000 s). A timed-out call says what to retry with (double the timeout, at most 300); at 300 it says to run the command detached and poll its output, or split it. A lone `runner.sh cancel <job id>` (the workspace's `claude-jobs/runner.sh`, optionally after `bash`) that exits 0 records who cancelled the job in its `cancelled_by` file (the turn's own kind, or the owner for an approved proposal, set by the dispatcher), and a lone `runner.sh status|result <job id>` of a cancelled job gets a `Cancelled by: ...` line before the `Exit code` trailer ("no cancel recorded by Nous" when there is no record) |
| `read_file` | task, debug, question | Read file contents. Pages at 400 lines / 48,000 chars: a result is a contiguous window, plus a trailer naming the next `offset` whenever lines remain past it (an explicit `limit` included). A single line over 48,000 chars is cut there, with a trailer saying so; never sampled by SmartCompress |
| `write_file` | task, creative | Write/create files. F099: an `internal_only` lineage with a root may write only under `<workspace>/intentions/<root>/` and, with `NOUS_F099_LINEAGE_SHELL` (the lineage can launch), `<workspace>/claude-jobs/prompts/`, plus the owner's directories in `NOUS_F099_LINEAGE_WRITE_DIRS` (`tool_policy.lineage_write_dirs`, shared with the lineage shell's redirections and its `mkdir -p`/`touch`/`cp`). The `write_path` refusal names the directories that turn may use |
| `spawn_task` | conversation, debug | Spawn a background subtask. F099: while `NOUS_INTENTIONS_ENABLED` is on, takes `intent` (one line: why, and what will be done with the result; refused if missing in a chat or MCP turn, generated in a background one) and `wake_policy` |
| `spawn_sync` | conversation, debug | Spawn a subtask and wait for its typed result. F099: while `NOUS_INTENTIONS_ENABLED` is on, takes `intent` (one line: why, and what will be done with the result; refused if missing in a chat or MCP turn, generated in a background one) and `wake_policy` |
| `schedule_task` | conversation, debug | Schedule a recurring/one-shot task. F099: while `NOUS_INTENTIONS_ENABLED` is on, takes `intent` (one line: why, and what will be done with the result; refused if missing in a chat or MCP turn, generated in a background one) and `wake_policy`. F101: optional `concurrency_policy` (`coalesce_if_active` default, `skip_if_active`, `always_enqueue`), `catch_up_policy` (`skip_missed` default, `enqueue_missed_with_cap`) and `catch_up_cap` (1 to 25), used by recurring schedules while `NOUS_SCHEDULE_POLICIES_ENABLED` is on |
| `dag_create` | conversation, debug | Create a dependency-tracked DAG of subtasks and checks. Its description states the node, wave and per-wave limits from `MAX_NODES`, `MAX_WAVES` and `MAX_PARALLEL_PER_WAVE` (`nous/dag/schemas.py`), and `source` is an enum built from `DAGCreateRequest.source`. Fix nodes do not count toward the wave or per-wave parallel limits. Every wave, parallel and stall-timeout violation comes back in one numbered error. A node whose inherited `NOUS_DAG_NODE_DEFAULT_STALL_TIMEOUT` exceeds its wall-clock timeout is stored with stall detection disabled (`0`), and the result says so in a `Note:` line; an explicit `stall_timeout_seconds` above the timeout is still refused. F099: while `NOUS_INTENTIONS_ENABLED` is on, takes `intent` (one line: why, and what will be done with the result; refused if missing in a chat or MCP turn, generated in a background one) and `wake_policy`. In an `internal_only` lineage it may not create an `approval` node, and it is offered only to a continuation turn whose root is below its limits. Typed waits: a `wait` node runs no model and no shell. Its `wait_for` is `job` (a Claude Code job id; `until` `finished`, the default, or `completed`), `pr` (`number`, optional `repo` defaulting to `NOUS_GITHUB_DEFAULT_REPO`, optional `head`; `until` `merged`, `closed`, `head_changed`, `checks_done` or `review_on_head`, with optional `reviewer`) or `file` (a workspace path with no hidden component; optional `nonempty`). The orchestrator evaluates it in-process (`nous/dag/waits.py`) every `completion_check_interval` until it holds, can no longer hold, or its timeout or `max_check_attempts` runs out. A `pr` wait polls at most once a minute (a shorter interval is raised to 60 s, with a `Note:` line); a GitHub error never fails it, and a rate limit backs every `pr` wait off for 15 minutes. A wait holds no subtask slot, but its DAG counts toward the active-DAG limit while it waits; a DAG cancel or a token-budget overrun cancels it. For a `check` or `wait` node with `max_check_attempts` and an interval, the timeout is raised to interval x attempts + one interval (a `Note:` line), and the DAG is refused when that exceeds `NOUS_DAG_NODE_MAX_TIMEOUT`. A DAG created by a background (`internal_only`) turn may wait only through typed conditions: it may carry no `completion_check` other than the exact built-in PR check (`python -m nous.dag.typed_checks pr ...`, which then runs without a shell); `dag_create` refuses one, and the orchestrator fails such a node at launch or poll |
| `dag_manage` | conversation, question, decision, debug | List, inspect (`status`, `recent`, `node_result`), cancel or retry nodes of DAGs. A cancel records who cancelled (the turn's own kind, or the owner for an approved proposal, set by the dispatcher) in the DAG's `postmortem`; a cancelled DAG's delivered outcome and its `status` name who cancelled it: the owner (with the surface), the agent's own turn, or the harness |
| `list_tasks` | conversation, question, decision, debug | List subtasks and schedules (F101: with each schedule's policies) |
| `cancel_task` | conversation, question, decision, debug | Cancel a subtask or schedule. `task_id` is a full id or an id prefix: hex with optional hyphens, up to 36 characters, with at least 8 hex digits (`TASK_ID_PREFIX_MIN`). It is resolved first against this agent's pending or running subtasks and active schedules, compared without hyphens on both sides (`replace(id::text, '-', '')`, a bound and LIKE-escaped value), so `3745ab2c1111` and `3745ab2c-1111` find the same task: one match is cancelled by its full id, more than one is an error listing each match's full id and the first 60 characters of its task, none is the usual "No pending subtask or active schedule" error. The durable ledger keeps a prefix as given (lowercased, hyphens and all, 6 to 36 characters with at least 6 hex digits; the same shape as `dag_manage`'s `dag_id`) instead of hashing it. F099: an `internal_only` lineage may cancel only its own lineage's work, checked on the resolved id; the runner still refuses an `internal_only` call whose `task_id` is not a whole UUID (`foreign_cancel`), so a lineage turn passes the full id |
| `web_search` | all | Search via multi-tier routing (Tavily/Exa/Brave) |
| `web_fetch` | all | Fetch and extract web content. F103: the result is screened for prompt injection and secrets in flag mode (logged, never changed; `NOUS_INJECTION_SCREEN_MODE`) |
| `browser_task` | conversation, task | F100 ([spec](../features/F100-browser-task.md)), registered only with `NOUS_BROWSER_TASK_ENABLED`: runs a goal in an isolated browser agent (headless Chromium, `browser_toolset_20260801`, its own `NOUS_BROWSER_TASK_MODEL`) limited to `allowed_domains` (public hosts only, enforced by an egress proxy that refuses any host resolving to a non-public address); one call at a time, a second one waits and may return `busy`; returns only a bounded text summary, the final URL without its query string and a saved screenshot path. Stops with `needs_confirmation` before logins, payments, purchases, accepting terms, sending messages or deletions. Callable from subtasks, DAG nodes, scheduled tasks and agent actions like `send_email`; not from heartbeat triage, background-model calls or `internal_only` continuation turns (`tool_policy.py`). Frame access is nominal while `NOUS_STABLE_TOOL_SET_ENABLED` is on (the default): every non-initiation frame gets the superset, so the context policy decides who may call. The outer agent gets `screenshot_path` and has `read_file`, so screenshot isolation is by convention. Class `external`. F103: the summary is screened for prompt injection and secrets in flag mode (logged, never changed) |
| `run_python` | conversation, question, debug, task | Execute Python with memory functions in scope. In-script `recall_deep()` runs the **same** `run_recall_pipeline` as the tool (since 2026-08-25 — it was `heart.search_facts`, facts-only, under a name promising the full retrieval) and returns dicts keyed `id`/`type`/`description`/`score`/`source`, with `content` kept as an alias of `description` for scripts written against the old `FactSummary` shape. Traced as F091 path `script`. Costs ~5s per call (prod p50), so budget a handful per script against the 90s deadline. |
| `send_file` | task, conversation, debug | Send files to Telegram (images as photos, rest as documents) |
| `heartbeat_check_create` | conversation, debug | Create a new dynamic heartbeat check (supports on_complete callback) |
| `heartbeat_check_manage` | conversation, debug | List, enable, disable, delete, or update dynamic checks |
| `push_surface` | conversation, debug (all frames under stable tool set) | F092: push a structured interactive surface to the companion app (templates: approval_gate, action_review, heartbeat_findings; `dedup_key` updates in place) |
| `propose_action` | continuation turns only (a per-turn extra tool, never registered with a dispatcher) | F099 Phase 2d: stage a call the lineage may not make itself (an outward send, a schedule, a shell command) for the owner to approve. `tool` must be registered and not one the lineage may call itself; spawn tools cannot be proposed; the arguments are checked against the tool's schema, may not start a name with `_`, and must render in at most 2000 characters (the owner reads the whole call). It never runs anything and is not terminal: the turn then ends with `resolve_intention(decision='ask')`, which publishes the proposal to the owner, who approves it in Telegram or through the REST route. A model has no tool that approves, rejects or answers. What an approved `schedule_task` starts is `internal_only`, like the lineage that proposed it |
