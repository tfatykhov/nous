# F034.4 — Heartbeat Completions

**Status:** PROPOSED  
**Priority:** P2 (quality polish — closes gaps across F034.1–F034.3)  
**Depends on:** F034.1, F034.2, F034.3 (all partially implemented)  
**Author:** Nous + Tim  
**Date:** 2026-04-04  

## Problem

F034.1–F034.3 are collectively 25/37 items fully implemented, with 5 partial and 7 not done (plus 3 Phase 2 deferred). The remaining gaps fall into three categories:

1. **Observability gaps** — The self-tuning engine adjusts parameters silently. No audit trail in Brain, no reports stored as facts, no Telegram visibility. Tim can't tell if tuning is working without hitting REST endpoints manually.
2. **Architectural inconsistency** — EmailCheck still manages its own `_seen_ids` dedup instead of going through FindingStore. One check path diverges from the lifecycle all other checks follow.
3. **Correctness gaps** — Rollback threshold uses an absolute 80% negative rate instead of the spec's "20% increase over previous cycle." Suppressed findings never resurface.

This spec consolidates all remaining items into three implementation batches, ordered by impact.

## Scope

### In scope (12 items)

**From F034.1 (3 items):**
- Suppression TTL — suppressed findings resurface after configurable TTL expires
- Per-check `fingerprint_key()` overrides — at least one check uses custom fingerprinting
- FindingStore persistence to Heart facts — survive restarts

**From F034.2 (4 items):**
- EmailCheck `_seen_ids` → FindingStore migration
- Drive folder→project mapping config mechanism
- Embedding-based pending action detection (upgrade from text search to cosine similarity)
- Temporal awareness Phase 2 — LLM-inferred implicit deadlines

**From F034.3 (5 items):**
- Brain decision recording for every tuning adjustment
- Tuning report stored as Heart fact
- Tuning report sent to Telegram
- Rollback threshold fix (80% absolute → 20% relative increase)
- Per-finding-type tuning (Phase 2 from original spec)

### Out of scope

- Auto-detect "Tim acts on finding" from cognitive sessions (blocked — run_turn has no tool visibility, needs architectural work beyond heartbeat)

## Design

### Batch 1 — Observability Loop (F034.3 polish)

**Priority:** Highest. These are all small additions to the existing tuning engine that make self-tuning visible and auditable.

#### 1a. Decision recording for tuning adjustments

After each parameter adjustment in `HeartbeatTuner.tune()`, call `Brain.record_decision()`:

```python
await brain.record_decision(
    description=f"Tuning {check.name}.{param}: {old_value} → {new_value} ({direction})",
    confidence=min(0.5 + (sample_count / 100), 0.9),  # scales with data
    category="process",
    stakes="low",
    context=f"Based on {sample_count} outcomes: {positive_rate:.0%} positive, {negative_rate:.0%} negative",
    reasons=[{
        "type": "empirical",
        "text": f"{sample_count} outcome signals over 30 days drove this adjustment"
    }],
    tags=["heartbeat", "tuning", "auto", check.name],
)
```

**Confidence scaling:** With 10 samples (minimum), confidence = 0.6. With 50+, confidence = 0.9. This reflects genuine uncertainty with small sample sizes.

**Affected files:** `nous/heartbeat/tuner.py` (or wherever `HeartbeatTuner` lives)  
**LOC estimate:** ~25 lines

#### 1b. Tuning report → Heart fact

After the tuning pass generates its report string, store it:

```python
await heart.facts.store(
    content=report_text,
    category="technical",
    subject="heartbeat-tuning",
    tags=["heartbeat", "tuning", "report"],
    confidence=1.0,
)
```

Only store if at least one parameter was actually adjusted (skip no-op tuning passes).

**Affected files:** `nous/heartbeat/tuner.py`  
**LOC estimate:** ~10 lines

#### 1c. Tuning report → Telegram

After storing the fact, send to Telegram using the same `_send_telegram()` pattern as HeartbeatRunner:

```python
if adjustments_made:
    await send_telegram(
        f"🔧 Heartbeat Tuning Report ({date.today().isoformat()})\n\n{report_text}",
        settings=settings,
        http_client=http_client,
    )
```

Extract `_send_telegram` into a shared utility (it currently lives on HeartbeatRunner) so the tuner can reuse it.

**Affected files:** `nous/heartbeat/tuner.py`, `nous/heartbeat/runner.py` (extract `_send_telegram`), new `nous/heartbeat/telegram.py` utility  
**LOC estimate:** ~30 lines (including extraction)

#### 1d. Rollback threshold fix

Current: rollback triggers if negative rate > 80% absolute.  
Spec: rollback triggers if negative rate **increased by >20%** since pre-adjustment snapshot.

```python
# Before adjustment
pre_negative_rate = self._get_negative_rate(check, outcomes_before)

# After adjustment runs for one cycle...
post_negative_rate = self._get_negative_rate(check, outcomes_after)

if post_negative_rate > pre_negative_rate + 0.20:
    # Rollback
    self._rollback(check, snapshot)
    await brain.record_decision(
        description=f"Rolled back {check.name} tuning: negative rate increased "
                    f"{pre_negative_rate:.0%} → {post_negative_rate:.0%}",
        confidence=0.85,
        category="process",
        stakes="medium",
        tags=["heartbeat", "tuning", "rollback", check.name],
    )
```

This requires storing the pre-adjustment negative rate in the snapshot (currently snapshots only store parameter values).

**Affected files:** `nous/heartbeat/tuner.py`  
**LOC estimate:** ~20 lines

**Batch 1 total:** ~85 lines, no new dependencies, all confined to tuner + one utility extraction.

### Batch 2 — Architectural Cleanup (F034.2 + F034.1)

#### 2a. EmailCheck `_seen_ids` → FindingStore

Replace EmailCheck's internal `_seen_ids: set[str]` with FindingStore-based dedup:

1. When EmailCheck processes an email, generate a fingerprint from `sha256(email_message_id + sender + subject_normalized)`
2. Before processing, check `finding_store.has_active(fingerprint)` — if exists, skip
3. If new, create finding via FindingStore (which handles state machine, escalation, etc.)
4. Remove `_seen_ids`, `_prune_seen_ids()`, and related code

This means email findings get the same lifecycle (state machine, escalation, daily digest inclusion, REST management) as all other findings.

**Migration:** On first run after deployment, `_seen_ids` is empty anyway (in-memory), so no migration needed. Previously-seen emails will be re-fingerprinted but FindingStore dedup handles re-occurrence correctly.

**Affected files:** `nous/heartbeat/checks.py` (EmailCheck)  
**LOC estimate:** ~40 lines changed (net reduction — removing _seen_ids code, replacing with FindingStore calls)

#### 2b. Suppression TTL

Add `suppression_ttl` to TrackedFinding (default: 72 hours for normal, 168 hours for low):

```python
@dataclass
class TrackedFinding:
    # ... existing fields ...
    suppressed_at: datetime | None = None
    suppression_ttl: timedelta = timedelta(hours=72)

    @property
    def suppression_expired(self) -> bool:
        if self.state != "suppressed" or self.suppressed_at is None:
            return False
        return datetime.now(UTC) - self.suppressed_at > self.suppression_ttl
```

In FindingStore's dedup check, if a suppressed finding's TTL has expired, transition it back to `new`:

```python
def check_finding(self, fingerprint: str, finding: Finding) -> str:
    existing = self._store.get(fingerprint)
    if existing and existing.state == "suppressed" and existing.suppression_expired:
        existing.state = "new"
        existing.suppressed_at = None
        return "resurfaced"
    # ... rest of dedup logic
```

**TTL defaults by urgency:**
- `low` → 168 hours (1 week)
- `normal` → 72 hours (3 days)  
- `high` → 24 hours (1 day)

**Affected files:** `nous/heartbeat/schemas.py` (or wherever TrackedFinding lives), FindingStore  
**LOC estimate:** ~25 lines

#### 2c. FindingStore persistence to Heart facts

On state transitions (new finding created, state change, escalation), serialize the FindingStore to a Heart fact:

```python
PERSISTENCE_KEY = "heartbeat:finding_store"

async def persist(self, heart: Heart) -> None:
    """Serialize active findings to a Heart fact for restart resilience."""
    payload = {
        fp: {
            "state": tf.state,
            "first_seen": tf.first_seen.isoformat(),
            "last_seen": tf.last_seen.isoformat(),
            "urgency": tf.urgency,
            "escalation_count": tf.escalation_count,
            "suppressed_at": tf.suppressed_at.isoformat() if tf.suppressed_at else None,
            "check_name": tf.check_name,
            "summary": tf.summary,
        }
        for fp, tf in self._store.items()
        if tf.state not in ("resolved",)  # don't persist resolved
    }
    await heart.facts.upsert(
        subject=PERSISTENCE_KEY,
        content=json.dumps(payload),
        category="technical",
        tags=["heartbeat", "finding_store", "persistence"],
    )

async def restore(self, heart: Heart) -> int:
    """Restore finding store from Heart fact on startup. Returns count restored."""
    facts = await heart.facts.search(PERSISTENCE_KEY, limit=1)
    if not facts:
        return 0
    payload = json.loads(facts[0].content)
    for fp, data in payload.items():
        self._store[fp] = TrackedFinding(**data)  # deserialize
    return len(self._store)
```

**When to persist:** Debounce — persist at most once per minute, or on shutdown. Don't persist on every finding (too noisy).

**Startup integration:** `HeartbeatRunner.start()` calls `finding_store.restore(heart)` before entering the tick loop.

**Affected files:** FindingStore class, `nous/heartbeat/runner.py` (startup hook)  
**LOC estimate:** ~60 lines

**Batch 2 total:** ~125 lines

#### 3c. Embedding-based pending action detection

Upgrade SelfInitiatedCheck from text search to cosine similarity against prototype embeddings:

```python
# Cached prototype embeddings (computed once at check init)
PENDING_PROTOTYPES = [
    "need to follow up on",
    "should investigate",
    "TODO: review",
    "promised to deliver",
    "waiting for response on",
]

async def _detect_pending_embeddings(self) -> list[Finding]:
    """Use embedding similarity instead of text search."""
    prototype_embeddings = await self._get_or_cache_embeddings(PENDING_PROTOTYPES)
    
    # Get recent facts and their embeddings
    recent_facts = await self._heart.facts.recent(days=14)
    
    for fact in recent_facts:
        fact_embedding = await self._heart.facts.get_embedding(fact.id)
        max_similarity = max(
            cosine_similarity(fact_embedding, proto)
            for proto in prototype_embeddings
        )
        if max_similarity >= self._similarity_threshold:
            findings.append(...)
```

**Dependency:** Requires Heart's embedding infrastructure to expose embeddings for cosine computation. If not available, fall back to current text search.

**Affected files:** `nous/heartbeat/checks.py` (SelfInitiatedCheck)  
**LOC estimate:** ~50 lines

## Success Metrics

- **Batch 1:** Every tuning adjustment appears in Brain decisions; Tim receives Telegram report on tuning day
- **Batch 2:** Zero heartbeat-related data loss across restarts (findings persist); EmailCheck findings appear in daily digest alongside all other findings  
- **Batch 3:** SelfInitiatedCheck finds pending items that text search misses; tuner can distinguish valuable vs noisy finding types within a single check

## Risks

- **Persistence bloat** — FindingStore fact could grow large if findings accumulate. Mitigated by excluding resolved findings and capping serialized store to 500 entries.
- **Telegram noise** — Tuning reports on weeks with no changes. Mitigated by only sending when adjustments were actually made.
- **Embedding availability** — Batch 3c depends on Heart exposing raw embeddings for cosine comparison. If not available, keep current text search as fallback.
