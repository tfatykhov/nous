# F092.1 — Ephemeral Micro-Apps

> **Addendum, not a replacement.** F092 Phase 0/1 shipped (#610) and Phase 2 is in flight.
> Nothing here changes Phase 0, 1, or 2. Every requirement below lands in Phase 3 or later
> and consumes Phase 2's output as-is.

---

## 1. The reframe

F092 v1 treated a composed surface as *a card the agent pushes* — one more notification
format. Tim's intent is different and larger:

> "With A2UI you will be able to create small UI apps when needed — an app for vacation, an
> app for sailing forecast — but only when they are needed. It's a UI app that only exists
> when we need it and then it disappears. And if we need it again you create it again."

**UI becomes a disposable artifact, not a shipped feature.** The same category as a chart or
a `.docx`: composed on demand, fitted to the moment, discarded after use. Rebuilt — not
restored — next time.

### Why this is architecturally cheaper than it sounds

The obvious objection to any agent-composed dashboard is staleness: build a view, then own
its freshness forever. That objection assumes the view persists. **Under rebuild-on-demand,
freshness is free by construction** — there is no sync problem because there is nothing to
sync. This is why F092.1 does *not* require a Goal/Project registry (F047) as a prerequisite,
which an earlier analysis wrongly assumed.

### The constraint that follows

If the app is disposable, **state must not live in the app.** A tap that means something
durable ("plate submitted") has to land in Heart/Brain before the app evaporates. The model:

```
Heart/Brain  =  durable state        (permanent)
Micro-app    =  view + control surface over it   (until closed)
```

Each new app is therefore a *query plus a component tree*, not a subsystem.

## 2. Resolved design questions

Four questions forked the design. All answered by Tim, 2026-08-29.

| # | Question | Answer | Consequence |
|---|---|---|---|
| Q7 | Read-only or interactive? | **Read-only, but navigable.** Links, drill-down, and predefined "more detail" buttons. **No free text inside an app.** | §3 — a new non-mutating action class. Big security simplification. |
| Q8 | Same app twice — stable or fresh? | **Fresh each time, within design guidelines we define.** | §4 — no recipe cache. Consistency comes from an enforced grammar, not from replay. |
| Q9 | Who triggers it? | **Both.** Tim asks, or Nous pushes unprompted. | §5 — `origin: agent` micro-apps, mandatory `dedup_key`. |
| Q10 | Lifetime? | **Until Tim closes it.** No TTL for now. | §6 — and this is the one answer that *reintroduces* staleness. Mitigated, not ignored. |

Q8 reverses my recommendation (I proposed caching the component tree per intent and
re-binding fresh data). Tim's answer is better on the axis that matters: a cached recipe
silently rots against a changing catalog and a changing situation, and "why does the sailing
app still show the old marina" becomes a debugging problem nobody wants. Guideline-constrained
fresh composition gets the same felt stability without the invalidation problem — provided
§4's grammar is genuinely enforced rather than merely documented.

## 3. Interaction model — the `navigable-readonly` action class

F092 §10 built an action system for *mutating* verbs: allowlist, handler registry, censor
gate, nonce, audit, compensation metadata. Micro-apps deliberately use **none of it.**

A micro-app declares `allowed_actions` drawn only from this closed set:

| Verb | Server round trip | Effect |
|---|---|---|
| `ui.navigate` | **No** — client-local | Tabs, accordion, modal open/close, list expand. Pure renderer state. |
| `ui.open_link` | No | Opens an external URL in a new tab. URL must be present in the surface's data model — never client-supplied. |
| `app.refine` | Yes | Predefined, parameterized "more detail" request. Nous recomposes and pushes `updateComponents` / `updateDataModel` to the same `surface_id`. |
| `app.refresh` | Yes | Re-runs the composition with current data. Same surface, new binding. |
| `app.close` | Yes | Terminal. Surface → `resolved`, `deleteSurface` emitted. |

**Rules**

1. **No handler in the `navigable-readonly` set may be `mutating`.** Enforced at registration:
   a micro-app surface whose `allowed_actions` contains any handler with `mutating=True` is
   rejected at creation, not at dispatch. Fail closed, fail early.
2. **`app.refine` params are enumerated at compose time.** The surface declares its own refine
   options (`{id, label, params}`); `POST /a2ui/action` validates the submitted `id` against
   that list. A refine button is *not* a free-form prompt with a nice label — that distinction
   is the whole security property.
3. **No free-text input inside a micro-app.** Free text remains exclusively in the Conversation
   surface (F092 §11.7, surface zero), which is an ordinary agent turn under the ordinary
   censor pipeline. F092 §10.10 is unchanged and now applies more narrowly.
4. **No evidence rows.** Micro-apps produce no `brain.decisions` audit entry — nothing happened
   that needs auditing. They follow the plain 30-day presentation-tier path of F092 §6.2.
5. **Mutating micro-apps are explicitly deferred** to F092.2 (§8). When a recurring app proves
   it needs a real verb, that verb graduates into the §10 registry with a compensation
   declaration — one verb at a time, with a censor review. It does not arrive by generalization.

## 4. The app grammar (Q8's "design guidelines")

Fresh composition without constraints produces a different-looking app every Friday, which is
unusable as a habit. Constraints go in the *grammar*, not in a cache.

### 4.1 Structural rules — machine-checked

Every micro-app surface MUST satisfy, in addition to F092 §9.2's structural checks:

- **Fixed skeleton.** `root` → `Column` containing, in order:
  `AppHeader` (title, subtitle, freshness stamp) · zero-or-one `StatRow` (≤4 `StatTile`) ·
  1–5 `Section` blocks · `AppFooter` (refine + refresh + close). Any other top-level
  arrangement is a validation failure.
- **Depth ≤ 5.** Component nesting beyond 5 levels is rejected.
- **Component budget ≤ 40** nodes per surface. Over budget → the composer must summarize
  and offer an `app.refine` drill-down instead of rendering everything.
- **Catalog subset.** Only `nous-core` + the `a2ui-basic` *display* components. The input
  components (`TextField`, `Slider`, `DateTimeInput`, `CheckBox`, `ChoicePicker`) are
  **banned in micro-apps** — they exist for the Conversation and form surfaces. This is the
  lint rule that mechanically enforces Q7.
- **Every section titled.** No anonymous blocks.
- **Freshness stamp mandatory** — see §6.

These become lint rules in the same validator Phase 2 builds for `nous-core`, and ship as
conformance fixtures (valid + each violation).

### 4.2 Archetypes — prompt-level, not enforced

The composer prompt carries three worked archetypes; the model picks one and fills it:

- **Status** — "where does X stand": StatRow of counts/deadlines, sections by subsystem,
  open items last. *(vacation, project status, DAG overview)*
- **Briefing** — "what's happening in window W": time-ordered `Timeline`, conditions summary,
  linked sources. *(sailing forecast, weekly digest)*
- **Ledger** — "list of things with attributes": `KeyValueTable` per item, sortable, drill-down
  per row via `app.refine`. *(bookings, decisions, findings)*

Archetype choice is recorded on the surface as `metadata.extensions.com_nous_archetype` so we
can measure whether the same intent keeps landing on the same archetype. **If it doesn't, the
grammar is too loose — that is the metric that tells us so.**

## 5. Triggering (Q9)

Micro-apps arrive two ways:

- **Pull** — Tim asks in chat. `origin: chat`. No notification; the app appears in the
  companion and Nous replies in Telegram with a deep link.
- **Push** — Nous composes unprompted, typically from a heartbeat or schedule ("it's Friday,
  here's the sailing app"). `origin: agent`. **`dedup_key` is mandatory** and MUST be
  `app:<intent-slug>` — so Friday's sailing app updates in place rather than stacking a
  fourteenth card. Priority defaults to `0` (ambient, no ping); a producer may raise to `1`
  only when the app carries a live deadline.

Pushed apps inherit the F092 §7.4 priority ladder unchanged. **No micro-app may ever be
priority 2** — blocking notification is reserved for escalations on irreversible actions, and
an ephemeral read-only view is by definition neither.

## 6. Lifetime, and the staleness it reintroduces (Q10)

`expires_at = NULL`. The surface stays `live` until `app.close`.

**Be explicit about the cost.** §1 argued that rebuild-on-demand makes freshness free. That
holds only at the instant of composition. A vacation app left open for three days is a
snapshot — the same staleness problem I claimed the ephemeral model dissolved. Q10's answer
brings it back through the side door, and pretending otherwise would be dishonest about the
design.

Three mitigations, in order of importance:

1. **Freshness stamp is mandatory in `AppHeader`** — "composed 13:34 UTC, 2h ago", rendered
   client-side from `composed_at`, and visually degraded (amber) past
   `a2ui_app_stale_after_s` (default 3600). The user always knows what they're looking at.
2. **`app.refresh` is always present** in `AppFooter`. One tap recomposes against current data.
3. **Concurrency cap, not a TTL.** Max `a2ui_max_live_apps` (default 8) live micro-apps per
   session. On overflow, the least-recently-viewed app is closed with a `deleteSurface` and a
   one-line note in the conversation. "Until you close it" is honored for everything you are
   plausibly still using; it does not mean unbounded accumulation.

A **stale-on-open sweep** is deliberately *not* included: auto-refreshing a surface the user
is not looking at spends tokens on nothing. Refresh is user-initiated or push-initiated.

## 7. Phasing changes

Phase 0, 1 unchanged and shipped. **Phase 2 unchanged and in flight** — F092.1 consumes its
output and adds no requirement to it. Any component gap discovered during Phase 3 is handled
in Phase 3, not by reopening Phase 2.

| Phase | F092 as written | F092.1 revision |
|---|---|---|
| **3** | LLM composition (~3 days) | **Ephemeral micro-apps (~1 week).** `compose_surface` + validate/repair (as specced) **plus**: the §4.1 grammar lint rules and fixtures; the §3 `navigable-readonly` action class with fail-closed registration; `AppHeader`/`AppFooter`/`Section`/`StatRow` in `nous-core`; freshness stamp; `app.refine` / `app.refresh` / `app.close`; `origin: agent` push path with mandatory `dedup_key`; concurrency cap + LRU eviction. |
| **4** | Polish — PWA, push, deep links (~3 days) | **Unchanged in scope, plus (~2 days):** multi-app switcher in the companion shell (several live apps at once is now the normal case), per-app deep links `/companion/a/<id>`, close-all. |
| **5** | *(new, ~3 days)* | **Measurement.** Archetype-stability metric (§4.2), compose success/repair/fallback rates, apps composed vs. opened vs. refreshed vs. closed-unused. Feeds the F092.2 decision on mutating verbs. |
| **6** | *(deferred, unsized)* | **F092.2 — mutating micro-apps.** Only if Phase 5 shows recurring apps whose users want to *act*. One verb at a time through the §10 registry with compensation metadata. |

**Net:** +~1.5 weeks over F092 as written. No new spec document is required beyond this one.

### Surface set amendment

F092 §11.6 "**Ad-hoc Composed** — `origin: chat`. The `compose_surface` output. Charts,
comparison tables, forms." is **replaced** by:

> **6. Micro-app** — `origin: chat | agent`, priority `0`–`1`, `expires_at: NULL`.
> An ephemeral, navigable, read-only application composed on demand for one intent —
> vacation status, sailing briefing, project ledger. Grammar-constrained (F092.1 §4),
> `navigable-readonly` actions only (F092.1 §3), lives until closed (F092.1 §6).
> Forms and free text are **not** here — they belong to surface 7.

## 8. Risks added by this addendum

| Risk | Severity | Mitigation |
|---|---|---|
| Long-lived open app shows stale data | **High** | §6 — mandatory freshness stamp with visual degradation, always-present refresh, concurrency cap. Accepted, not eliminated. |
| Fresh-every-time produces inconsistent UI, app feels unreliable | **High** | §4.1 machine-checked skeleton + §4.2 archetypes. §4.2's archetype-stability metric is the *detector* — if the same intent drifts across archetypes, tighten the grammar or promote that intent to a template builder. |
| Composer over-renders (dumps everything into one app) | Medium | Component budget ≤40 and depth ≤5, enforced. Over budget → summarize + `app.refine`. |
| Micro-apps drift toward mutating actions by convenience | Medium | Fail-closed registration check (§3.1) makes it impossible by accident. Graduation path is explicit and gated (§3.5, Phase 6). |
| `app.refine` becomes a free-text prompt in disguise | Medium | Enumerated refine options validated server-side (§3.2). Lint bans input components outright (§4.1). |
| Token cost of recomposing on every ask | Low | Template builders still take precedence for anything recurring (F092 §9.1). Phase 5 measures it. |
| Unbounded live surfaces | Low | Concurrency cap with LRU eviction (§6.3). |

## 9. Worked example — the vacation app

Intent: *"show me my vacation plans."* Archetype: **Status**.

```
AppHeader   "Italy — Sep 5–20, 2026"  ·  "departs in 7 days"  ·  composed 13:34 UTC
StatRow     [ 7 days out ] [ 5/5 booked ] [ €811 due Sep 9 ] [ 2 blockers ]
Section     "Flights"        KeyValueTable  (UA MZHEN1, out, back, seats, cost)
Section     "Where you sleep" Timeline      (5 stays, gaps highlighted)
Section     "Car"            KeyValueTable  (pickup, drop, one-way fee, legs)
Section     "Blockers"       List           (2 blank plates, Tre Cime deadline Sep 7 10:00)
Section     "Still unbooked" List           (Scrovegni, Seceda, Monte Baldo, Biennale, taxi)
AppFooter   refine: [Day-by-day] [Costs] [Just the blockers]  ·  refresh  ·  close
```

`allowed_actions`: `["ui.navigate", "ui.open_link", "app.refine", "app.refresh", "app.close"]`
— all non-mutating. `app.refine{id: "blockers"}` recomposes the same surface as a **Ledger**
scoped to open items. Nothing in this app can change a booking; asking Nous to *do* something
about a blocker is a conversational turn in surface 7.

## 10. What this addendum does not decide

- **F047 (Goal/Project Registry)** is no longer a prerequisite (§1) but remains independently
  useful — it would make the vacation app's composition a lookup rather than an assembly.
  Unblocked, unscheduled.
- **Mutating verbs** — deferred to Phase 6 / F092.2, gated on Phase 5 measurement.
- **Offline access to a live app** — out of scope; F092 §12.0's PWA revisit triggers apply.
