# F078.1 — Guarded `send_email` tool + recipient allowlist

**Status:** 📝 Draft (2026-06-05)
**Parent:** F078 (correct-side censors). **Decision:** forge `72c0393b`.
**Pattern reference:** `nous/api/telegram_tools.py` (`send_file`, decision `73ed8f2d`) — isolated tool module + `register_*_tools()` wired conditionally in `main.py`.

## Problem
The exfil failure mode F078 could not fully close: a subtask once **hallucinated a recipient and emailed a stranger**. Email is sent by **agent-authored code** (`bash → python3 smtplib`, per the seeded `send_email` procedure — `scripts/seed_procedures.js:13-31`); there is **no chokepoint**. The discriminator is the **recipient**, not the message text, so a text-regex censor can't tell a daily-report-to-Tim from an exfil-to-stranger — which is why F078 kept the email censor as advisory `steer` (BC: refuse/abort would break the daily email senders).

## Goal
Add a **guarded chokepoint** — a real `send_email` tool that validates the recipient against an allowlist before sending — **additively**, without breaking the existing bash+smtplib path.

## Non-negotiable: BC invariant
- The existing agent-authored bash+smtplib path **must keep working** (daily email tasks). F078.1 is **additive** — it adds the safe tool alongside; it does not remove or block the ad-hoc path.
- Closing the hole *fully* = migrating the daily tasks + the `send_email` procedure to the tool (operational, over time). v1 ships the tool + steers the agent to it.

## Design

### New module `nous/api/email_tools.py` (mirror `telegram_tools.py`)
A `send_email` tool closure + `_SEND_EMAIL_SCHEMA` + `register_email_tools(dispatcher, settings)`.

`send_email(to, subject, body, cc=None)`:
1. **Enabled + creds check.** If `not settings.email_tool_enabled` or `not settings.email_user`/`email_password` → return a clear error (no send).
2. **Recipient allowlist (the core guard).** Parse `to` + `cc` (accept str or list). Each address must be in the allowlist (`settings.email_allowlist`, CSV, **case-insensitive exact match**). Any address **not** in the allowlist → **reject, no send**, with a message naming the offending address and how to allow it (`NOUS_EMAIL_ALLOWLIST` / operator). **Empty allowlist ⇒ reject all** (safe default).
3. **Secret scan (secondary guard).** Scan `subject + body` for obvious secrets — `sk-[A-Za-z0-9]{16,}`, `AKIA[0-9A-Z]{12,}`, `password\s*[:=]`, `Bearer [A-Za-z0-9._-]{20,}`, long base64/hex tokens. On hit → **reject, no send** ("email appears to contain a secret"). (Covers the `sending email with sensitive data` censor intent.)
4. **Rate limit.** In-process sliding window, `settings.email_max_per_hour` (default 5; matches the existing censor rule). Use `time.monotonic()` (NOT datetime). Over limit → reject.
5. **Send.** `smtplib` is blocking → run via `await asyncio.to_thread(...)`. STARTTLS to `settings.email_smtp_host:email_smtp_port`, login with `email_user`/`email_password`, `From = settings.email or email_user`, MIME via `email.mime.text.MIMEText`.
6. **Sanitize exceptions (security — lesson from `73ed8f2d`).** smtplib/login errors can embed credentials/host. Catch all, log full server-side, but return only a **generic** "email send failed: <ExceptionType>" to the model — never the raw smtplib message.
7. Return a structured success ("sent to X") or the rejection reason.

### Config (`nous/config.py`)
- `email_allowlist: str = ""` (`NOUS_EMAIL_ALLOWLIST`, CSV; operator seeds with `Tfatykhov@gmail.com`, `maechkina@gmail.com`, + daily-task recipients).
- `email_tool_enabled: bool = True` (`NOUS_EMAIL_TOOL_ENABLED`).
- `email_max_per_hour: int = 5` (`NOUS_EMAIL_MAX_PER_HOUR`).
- `email_smtp_host: str = "smtp.gmail.com"`, `email_smtp_port: int = 587`.
- **`email_allowlist_file: str = ""` (`NOUS_EMAIL_ALLOWLIST_FILE`) — F078.1.1, hot-reloadable.** A file (one address per line or CSV, `#` comments) read **at send-time**, mtime-cached, **fail-closed** on error (never widens on read failure). **Effective allowlist = `email_allowlist` (env, static base) ∪ file contents.** Appending an address takes effect on the **next send with no restart** — this is the managed list (the env CSV is just an optional static base). Operator manages additions by editing the file (or the agent appends via `bash`).
(Reuses existing `email`, `email_user`, `email_password`.)

### Wiring
- `main.py`: `if settings.email_user: from nous.api.email_tools import register_email_tools; register_email_tools(dispatcher, settings)` — near the telegram wiring (~line 496) / email-heartbeat block (~634). Gate on `email_user` (the SMTP login).
- `runner.py FRAME_TOOLS`: add `"send_email"` to `conversation` and `debug` (`task` is `["*"]`). Mirror `send_file`.
- **Steer the agent to it (additive):** update the seeded `send_email` procedure (`scripts/seed_procedures.js`) to "prefer the `send_email` tool (recipient-allowlisted); fall back to bash+smtplib only if unavailable." (Operator separately updates the prod `send_email` procedure + the email steer censor directive to point at the tool.)

## Tests (`tests/test_email_tools.py`) — never send for real (monkeypatch `smtplib`/`asyncio.to_thread`)
- allowlist: in-list → sends; off-list (incl. one bad in a cc list) → reject, no send.
- empty allowlist → reject all.
- secret scan → reject on a planted `sk-...` / `password:` in body.
- rate limit → 6th send in the window rejected.
- creds absent / `email_tool_enabled=False` → clear error, no send.
- exception sanitization → a raised smtplib error surfaces a generic message, NOT the raw text.

## Rollout
Ship safe-by-default: tool registered, **empty allowlist = reject-all**, so it cannot send until the operator sets `NOUS_EMAIL_ALLOWLIST`. Then operator seeds the allowlist, updates the procedure + email steer directive, and migrates the daily tasks to the tool. The ad-hoc path stays available throughout (BC).

## Out of scope
- Auto-migrating the daily tasks (operational).
- Removing/blocking the bash+smtplib path (would break BC).
- Per-recipient policy / attachments (later if needed; `send_file` already handles Telegram files).

## F078.1.2 — attachments (2026-06-06)
`send_email` gained an optional `attachments` param (file path or list) so report-style emails (a generated `.docx`/`.pdf`) can move onto the guarded tool — a prerequisite for migrating the daily email tasks off bash+smtplib.

- With attachments → `MIMEMultipart` (`MIMEText` body + one `MIMEApplication` part per file); without → plain `MIMEText` (v1 behavior unchanged).
- Each path validated **before any send**: must be a readable regular file; **total size ≤ `NOUS_EMAIL_MAX_ATTACHMENT_MB`** (default 25, Gmail's limit). Invalid path / oversize → reject, no send.
- All v1 guards run first (allowlist → secret-scan → rate-limit), so an off-allowlist send is rejected before files are even read.
- **Attachment *contents* are not secret-scanned** (binary; unreliable). The recipient allowlist (trusted recipients only) is the guard, and the tool is still strictly safer than the unguarded bash+smtplib path it replaces.
- Config: `email_max_attachment_mb: int = 25` (`NOUS_EMAIL_MAX_ATTACHMENT_MB`).
