# F092.2 — Agent-Bound Actions in Micro-Apps

**Status:** Implemented, land-dark (`NOUS_A2UI_AGENT_ACTIONS_ENABLED=false`).

## Problem

Micro-apps (F092.1) are read-only: every action-router verb a composed app
holds is `app.close`, and every existing handler is hard-coded Python. There
is no route from a user tapping the app back to the *agent* — the user can
look at a dashboard but cannot ask the agent to act on what it shows.

## Design

A tap becomes a background agent turn that acts and recomposes the app.

### Declaration — the F095 trust split

`compose_surface` gains `agent_actions: [{id, label, instruction}]` (≤4,
label ≤40 chars, instruction ≤500 chars, slug ids, validated at the tool
layer). Actions enter **only** through the agent's own tool call — the inner
compose LLM never sees or authors them, exactly like F095 `data_sources`.
The schema advertises the parameter only when the flag is on (the
agent_script lesson: never describe a param the server rejects).

The caps are load-bearing: the instruction is stored and replayed into a
future agent turn with nobody in the loop, so it is bounded at declaration —
the only moment the agent is deliberate about it.

### Stamping — the footer renders what the server validated

`compose()` stamps `agentActions: [{id, label}]` onto the AppFooter (the
refineOptions pattern; the instruction never reaches the client) and adds
`app.act` to `allowed_actions` — which is server-constructed, so the compose
LLM cannot widen it. `push_built`'s fail-closed guard widens to
`{app.close, app.act}` only when the flag is on AND `app_spec` declares
actions. Declared actions survive:

- **refine** — re-passed from the *surviving* app_spec exactly like theme
  (gated on the flag, so the kill switch also sheds buttons on next refine);
- **fallback** — a degraded render most needs its "ask the agent" buttons
  (a tap can recompose it into a real app), and dropping them would make a
  refine-that-falls-back silently strip buttons app_spec still declares;
- **refresh** — components untouched, nothing to re-stamp.

### Dispatch — `app.act` through the existing pipeline

The tap posts `app.act {actionId}` through the full F092 gate: allowlist →
nonce → rate limit → censor (mutating) → audit. The handler then:

1. **Kill switch** — refuses when the flag is off (surfaces composed while
   it was on stay renderable; taps refuse loudly).
2. Validates `actionId` against **server truth** (`app_spec.agent_actions`).
3. **Server-side double-tap guard** — a fresh `pendingAction` on the surface
   rejects the tap. Client button-disabling is UX; this is the control: each
   tap spawns an LLM turn against `NOUS_SUBTASK_MAX_CONCURRENT=3`.
4. Spawns a **subtask** (frame `task` — has `compose_surface`) and stamps
   `/meta/pendingAction = {id, label, at}`.

### The subtask prompt

Carries the action's stored instruction, a **bounded** (4k chars) data-model
snapshot wrapped in S2 DATA/INSTRUCTION delimiters — the snapshot can
contain externally-fetched text (agent_script sources hit arbitrary APIs)
and it rides into a turn holding tools — and an `<app-config>` block with
the `dedup_key`, `data_sources`, and `agent_actions` to re-declare, so the
recompose lands on the same surface and keeps it live and actionable.

### Update path — recompose-via-dedup only

The agent updates the app by calling `compose_surface` with the same
`dedup_key`: dedup replacement preserves `surface_id` and replaces the data
model wholesale, which **clears the pending stamp for free**. No data-patch
tool in v1 — it would bypass binding validation and fake provenance;
recompose reuses all of it. (`dedup_key` is always present: compose
auto-assigns `app:<intent-slug>`.)

### Failure honesty — watcher + timestamp

An in-process watcher polls the subtask; on failure, cancellation, timeout,
or completed-without-recomposing, it clears `pendingAction` and writes
`/meta/actionError` — **only if the stamp is still its own** (a successful
recompose or a newer action means nothing to clean up). Watcher tasks are
held in a strong-ref set (asyncio holds task refs weakly).

**Known limitation (the F087 restart hole):** the watcher dies with the
process. That is why the client *also* derives staleness from the
`pendingAction.at` timestamp: past 5 minutes the buttons re-enable and the
footer renders "no update arrived" — a dead watcher degrades to an honest
stale note, never an infinite spinner.

### Renderer

AppFooterView renders the stamped buttons (accent-bordered, before refine
options). A fresh `pendingAction` disables all agent-action buttons and
suffixes the busy one with an ellipsis; a stale one re-enables them with the
honest note; `/meta/actionError` renders in the footer's error slot.

## Flags

| Variable | Default | Meaning |
|---|---|---|
| `NOUS_A2UI_AGENT_ACTIONS_ENABLED` | `false` | Master switch. Land-dark: a UI tap becomes an LLM turn holding tools, executing a stored instruction with nobody in the loop — same exposure-window reasoning as F095/F090.1 (flipped deliberately by an operator, never acquired on deploy). |
| `NOUS_A2UI_AGENT_ACTION_TIMEOUT_SECONDS` | `300` | Subtask watcher deadline AND the double-tap freshness window. |

## Deferred to v2

- **Per-component/inline actions** (per-row "retry this task") — v1 is
  footer-level only, which keeps the compose LLM structurally unable to
  author actions anywhere.
- **Free-text input** riding with a tap.
- Synchronous RPC variant for fast actions.

## Tests

`tests/test_a2ui_agent_actions.py` (21 unit + 5 postgres-gated integration)
and 4 AppFooterView vitest cases: declaration caps, footer/allowlist/spec
stamping, instruction never reaching the client, schema gating, push-guard
rejects, prompt contract, watcher honesty (4 cases), full `app.act` dispatch
with a fake subtask manager, double-tap rejection, kill switch on existing
surfaces, refine re-stamp from surviving spec, and the renderer's
pending/stale/error states.
