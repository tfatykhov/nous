# 012.2 — Subtask Enhancements (Light)

**Status:** Ready  
**Parent:** F013 (Frame Splitting — deferred)  
**Replaces:** 012.1 (full frame-splitting — deferred)  
**Estimated effort:** ~4-5 hours  
**Branch:** `012.2-subtask-enhancements`

## Motivation

F013 proposed a full parallel-frame paradigm (`split_frames` tool, sync barriers, frame
merging). After review (composite 7.0/10) and deliberation, the full spec was deferred as
too complex (~10-13h, paradigm shift from fire-and-forget to sync barrier).

This light version captures six targeted wins — three from the F013 analysis plus three
execution guardrails validated by industry research (2025-2026):

**Core enhancements (from F013):**

1. **Frame-aware subtasks** — store `frame_type` on the Subtask model so workers can
   apply frame-appropriate behavior
2. **Enhanced worker context** — when `frame_type` is set, enrich the worker's system
   prompt with frame-specific instructions and tool guidance
3. **Synchronous subtasks** — add `await_result` flag to `spawn_task` so callers can
   wait for results inline instead of fire-and-forget only

**Execution guardrails (research-backed):**

4. **No-nesting rule** — inline subtasks cannot spawn further subtasks (dominant industry
   pattern: Claude Code, Crush, mini-claude-code)
5. **Tool call limit** — cap subtask tool invocations at 20 to prevent runaway loops
6. **Reduced inline timeout** — `await_result` subtasks default to 90s instead of 300s
   to prevent parent turn starvation

### Research basis for guardrails

A review of 7 frameworks and 2 papers (Claude Code, LangChain Deep Agents, Charmbracelet
Crush, mini-claude-code, Google ADK, OpenAI Agents SDK, ReDel, ypi) found that
**nesting prevention is the dominant pattern** in production agent systems:

- **Claude Code** — subagents CANNOT spawn subagents (tool excluded from sub-agent set)
- **Crush** — `ParallelAgentTool` NOT available to sub-agents
- **mini-claude-code** — explicitly prevents recursion via tool filtering
- **ReDel** (allows recursion) — documented _overcommitment_ and _undercommitment_
  failure modes where recursive agents delegate excessively or refuse to delegate
- **ypi** (bounded recursion) — requires 5 guardrails: depth limit, PATH scrubbing,
  call count, budget, timeout

The no-nesting + tool call limit + reduced timeout combination provides the safety of
the dominant pattern with minimal implementation complexity.

## Item 2: Enhanced Worker Context Assembly

### Current state

The worker in `subtask_worker.py` calls `runner.run_turn()` with a minimal
`system_prompt_prefix`:

```python
system_prefix = (
    "You are a subtask worker. Execute the following task precisely and "
    "return your result. Do not ask clarifying questions — work with what "
    "you have. Be concise but thorough.\n\n"
    f"Task: {subtask.task}"
)
```

The runner's `run_turn()` → `pre_turn()` does run the full cognitive pipeline (recall,
censors, identity), but frame selection is auto-detected from the task string, which may
not match the caller's intent.

### What changes

**Worker: `nous/handlers/subtask_worker.py` — `_process_subtask()`**

When `subtask.frame_type` is set, build a richer system prefix using frame-specific
instructions from `FRAME_TOOLS`:

```python
from nous.api.runner import FRAME_TOOLS

async def _process_subtask(self, subtask: Subtask) -> None:
    # Build system prefix
    base_prefix = (
        "You are a subtask worker. Execute the following task precisely and "
        "return your result. Do not ask clarifying questions — work with what "
        "you have. Be concise but thorough."
    )

    # Frame-aware enrichment
    frame_instruction = ""
    if subtask.frame_type and subtask.frame_type in FRAME_TOOLS:
        tool_instruction = FRAME_TOOLS[subtask.frame_type].get("instruction", "")
        if tool_instruction:
            frame_instruction = (
                f"\n\n## Frame: {subtask.frame_type}\n"
                f"{tool_instruction}"
            )

    system_prefix = f"{base_prefix}{frame_instruction}\n\nTask: {subtask.task}"

    # ... rest of run_turn call unchanged
```

This gives the worker frame-appropriate guidance (e.g., research frame gets
`web_search`/`web_fetch` instructions, task frame gets `bash`/`write_file` instructions)
without modifying the cognitive layer or runner.

### Frame-specific behavior examples

| frame_type | Effect |
|---|---|
| `research` | Worker gets web_search/web_fetch tool instructions |
| `task` | Worker gets bash/write_file/read_file instructions |
| `decision` | Worker gets record_decision/recall_deep instructions |
| `debug` | Worker gets bash/read_file diagnostic instructions |
| `None` | Current behavior — auto-detect from task text |

## Item 3: Synchronous Subtasks (`await_result`)

### Current state

`spawn_task` is always fire-and-forget. The tool handler queues the subtask, returns
`"Subtask queued..."`, and the background worker picks it up later. Results arrive via
injection into the next conversation turn (011.2).

This forces a multi-turn pattern for tasks where the parent needs the result immediately
(e.g., "research X and then use the result to do Y").

### What changes

**Tool schema: `nous/api/tools.py` — `_SPAWN_TASK_SCHEMA`**

Add `await_result` property:

```python
"await_result": {
    "type": "boolean",
    "default": False,
    "description": "If true, wait for subtask completion and return result inline. Default false (fire-and-forget).",
},
```

**Tool handler: `nous/api/tools.py` — spawn_task handler**

When `await_result=True`, run the subtask inline instead of queueing for the background
worker:

```python
# Constants for subtask guardrails (Items 5 & 6)
SUBTASK_TOOL_CALL_LIMIT = 20
INLINE_SUBTASK_DEFAULT_TIMEOUT = 90  # seconds

async def _handle_spawn_task(self, args: dict, session_id: str) -> str:
    task = args["task"]
    priority = args.get("priority", "normal")
    notify = args.get("notify", True)
    frame_type = args.get("frame_type")          # NEW
    await_result = args.get("await_result", False)  # NEW

    # Apply reduced default timeout for inline subtasks (Item 6)
    if await_result:
        timeout = args.get("timeout", INLINE_SUBTASK_DEFAULT_TIMEOUT)
    else:
        timeout = args.get("timeout", 300)

    # Create subtask record (for tracking either way)
    subtask_id = await self._heart.subtasks.create(
        parent_session_id=session_id,
        task=task,
        priority=priority,
        timeout_seconds=timeout,
        notify=notify,
        frame_type=frame_type,
    )

    if not await_result:
        # Fire-and-forget (existing behavior)
        return f"Subtask {subtask_id} queued (priority: {priority})"

    # Synchronous execution — run inline
    try:
        subtask_session_id = f"subtask-{subtask_id}"

        # Build system prefix (same logic as worker)
        from nous.api.runner import FRAME_TOOLS
        base_prefix = (
            "You are a subtask worker. Execute the following task precisely and "
            "return your result. Do not ask clarifying questions — work with what "
            "you have. Be concise but thorough."
        )
        frame_instruction = ""
        if frame_type and frame_type in FRAME_TOOLS:
            tool_instruction = FRAME_TOOLS[frame_type].get("instruction", "")
            if tool_instruction:
                frame_instruction = f"\n\n## Frame: {frame_type}\n{tool_instruction}"

        system_prefix = f"{base_prefix}{frame_instruction}\n\nTask: {task}"

        # Run via runner with guardrails (Items 4 & 5)
        response, _, _ = await asyncio.wait_for(
            self._runner.run_turn(
                session_id=subtask_session_id,
                user_message=task,
                system_prompt_prefix=system_prefix,
                skip_episode=True,
                is_subtask=True,                     # NEW — enables guardrails
                max_tool_calls=SUBTASK_TOOL_CALL_LIMIT,  # NEW — Item 5
            ),
            timeout=timeout,
        )

        # Update subtask record
        await self._heart.subtasks.complete(subtask_id, response)

        return f"[Subtask {subtask_id} completed]\n\n{response}"

    except asyncio.TimeoutError:
        await self._heart.subtasks.fail(subtask_id, "Timeout")
        return f"[Subtask {subtask_id} timed out after {timeout}s]"
    except Exception as e:
        await self._heart.subtasks.fail(subtask_id, str(e))
        return f"[Subtask {subtask_id} failed: {e}]"
```

### Key design decision: inline execution vs. queue-and-poll

For sync subtasks, we run inline (directly calling `runner.run_turn`) rather than
queueing to the background worker and polling for completion. Rationale:

- **Simpler** — no pub/sub or polling mechanism needed
- **Lower latency** — no queue delay
- **Same pipeline** — uses same runner.run_turn() as the background worker
- **Still tracked** — subtask record created for history/debugging
- **Timeout respected** — asyncio.wait_for enforces the limit

The trade-off is that sync subtasks run in the main tool loop, consuming a turn slot.
This is acceptable because the caller explicitly chose to wait.

### Interaction with existing tool loop

The sync subtask runs as a nested `run_turn` call. This works because:
- It uses a separate session_id (`subtask-{id}`)
- It gets its own conversation context
- The runner is stateless per-call (no global locks)
- Tool loop max iterations still apply to the inner call independently
- Nesting is blocked — the inner call cannot spawn further subtasks (Item 4)

## Item 4: No-Nesting Rule (Research-Backed)

### Problem

Without a nesting guard, an inline subtask (`await_result=True`) could itself call
`spawn_task(await_result=True)`, creating nested inline execution. This creates:

- **Stack depth risk** — triple nesting: parent → subtask → sub-subtask
- **Timeout cascade** — each layer's timeout stacks (300s × 3 = 900s worst case)
- **Token explosion** — each layer holds its full context in memory
- **Overcommitment** — ReDel research documented recursive agents delegating excessively
  instead of doing work directly

### Industry precedent

This is the **dominant pattern** in production systems:

- **Claude Code** — subagents cannot spawn subagents (tool excluded from set)
- **Crush** — `ParallelAgentTool` not available to sub-agents
- **mini-claude-code** — explicitly prevents recursion via tool filtering
- Only **ypi** allows bounded recursion, requiring 5 separate guardrails

### What changes

**Runner: `nous/api/runner.py` — `run_turn()`**

Accept `is_subtask` flag that controls tool availability:

```python
async def run_turn(
    self,
    session_id: str,
    user_message: str,
    *,
    system_prompt_prefix: str | None = None,
    skip_episode: bool = False,
    is_subtask: bool = False,              # NEW
    max_tool_calls: int | None = None,     # NEW (Item 5)
) -> tuple[str, str, dict]:
    # ... existing setup ...

    # Build tool set
    tools = self._build_tools()
    if is_subtask:
        # Remove spawn_task and schedule_task from subtask tool set
        tools = [t for t in tools if t["function"]["name"] not in (
            "spawn_task", "schedule_task"
        )]

    # ... rest of run_turn ...
```

**Worker: `nous/handlers/subtask_worker.py` — `_process_subtask()`**

Background worker subtasks also pass `is_subtask=True`:

```python
response, _, _ = await self._runner.run_turn(
    session_id=subtask_session_id,
    user_message=subtask.task,
    system_prompt_prefix=system_prefix,
    skip_episode=True,
    is_subtask=True,                     # NEW
    max_tool_calls=SUBTASK_TOOL_CALL_LIMIT,  # NEW (Item 5)
)
```

### Scope of exclusion

Tools **removed** from subtask tool set:
- `spawn_task` — prevents nesting entirely
- `schedule_task` — subtasks should not create recurring jobs

Tools **retained** in subtask tool set:
- All memory tools (`recall_deep`, `recall_recent`, `learn_fact`, `record_decision`, `create_censor`)
- All workspace tools (`bash`, `read_file`, `write_file`)
- All web tools (`web_search`, `web_fetch`)

This matches Claude Code's approach: subtasks can do real work, they just can't delegate.

## Item 5: Tool Call Limit per Subtask

### Problem

A subtask without a tool call limit can loop indefinitely — calling `bash`, checking
results, calling `bash` again — burning tokens and time. The runner's existing
`max_iterations` config applies globally but isn't tuned for subtask scope.

### What changes

**Runner: `nous/api/runner.py` — tool loop**

Honor `max_tool_calls` parameter when set:

```python
async def run_turn(self, ..., max_tool_calls: int | None = None, ...) -> ...:
    # ... existing setup ...

    tool_call_count = 0

    while has_tool_calls:
        tool_call_count += len(current_tool_calls)

        if max_tool_calls and tool_call_count >= max_tool_calls:
            # Force completion — append a system message and break
            messages.append({
                "role": "system",
                "content": (
                    f"Tool call limit reached ({max_tool_calls}). "
                    "Provide your best answer with what you have so far."
                )
            })
            break

        # ... process tool calls as normal ...
```

### Configuration

```python
SUBTASK_TOOL_CALL_LIMIT = 20  # defined in tools.py alongside handler
```

- **20** chosen as a reasonable ceiling: enough for research (5-6 web searches +
  fetches) or code tasks (10-12 bash calls), but catches runaway loops
- Only enforced when `max_tool_calls` is passed — existing non-subtask turns unaffected
- Subtask is NOT killed — it gets a graceful "wrap up now" signal

## Item 6: Reduced Default Timeout for Inline Subtasks

### Problem

The current default timeout is 300s (5 minutes). For an inline (`await_result=True`)
subtask, this means:

- Parent turn is paused for up to 5 minutes
- If the parent spawns 3 sequential inline subtasks, that's up to 15 minutes
- User sees no response during this time (on Telegram, etc.)

### What changes

**Constant in `nous/api/tools.py`:**

```python
INLINE_SUBTASK_DEFAULT_TIMEOUT = 90  # seconds
```

**Applied in `_handle_spawn_task`** (shown in Item 3 code):

```python
if await_result:
    timeout = args.get("timeout", INLINE_SUBTASK_DEFAULT_TIMEOUT)  # 90s
else:
    timeout = args.get("timeout", 300)  # 5min for background tasks
```

### Rationale

- **90 seconds** is enough for most inline tasks (research lookup, code check, decision
  recording) but prevents parent starvation
- Fire-and-forget subtasks keep 300s default — they run in background, no starvation risk
- Caller can still override with explicit `timeout` parameter if needed
- 3 sequential inline subtasks worst case: 270s (4.5 min) instead of 900s (15 min)

## Migration Notes

- **Backward compatible** — all new fields/params are optional with sensible defaults
- **No data migration** — existing subtasks have `frame_type=NULL` (auto-detect)
- **Schema change only** — single ALTER TABLE, no data backfill
- **Tool schema change** — LLM sees new optional params in spawn_task, existing
  calls continue to work without them
- **Runner signature change** — new optional kwargs `is_subtask` and `max_tool_calls`,
  defaults preserve existing behavior

## Testing Plan

1. **Migration** — verify `frame_type` column added, NULL for existing rows
2. **spawn_task without new params** — existing behavior unchanged
3. **spawn_task with frame_type="research"** — verify worker gets research frame instructions
4. **spawn_task with await_result=True** — verify inline execution returns result
5. **spawn_task with await_result=True + timeout** — verify timeout handling (90s default)
6. **spawn_task with frame_type + await_result** — verify both work together
7. **No-nesting** — inline subtask attempts `spawn_task` → tool not available (no error, just absent from tool list)
8. **No-nesting (background)** — background worker subtask also cannot spawn further subtasks
9. **Tool call limit** — subtask with 20+ tool calls gets graceful "wrap up" signal
10. **Tool call limit (non-subtask)** — normal turns NOT affected by subtask limit
11. **Timeout differentiation** — `await_result=True` defaults to 90s; fire-and-forget defaults to 300s
12. **Explicit timeout override** — `spawn_task(await_result=True, timeout=180)` uses 180s, not 90s

## Relationship to F013

This spec extracts the most valuable pieces from F013 without the paradigm shift:

| F013 concept | 012.2 equivalent |
|---|---|
| Frame-typed sub-agents | `frame_type` on spawn_task |
| Context propagation | Worker frame-aware system prefix |
| Sync barrier (join) | `await_result=True` inline execution |
| Sub-agent safety | No-nesting + tool call limit + reduced timeout |
| `split_frames` tool | Not implemented (deferred) |
| Parallel execution | Not implemented (deferred) |
| Result merging/synthesis | Not implemented (deferred) |

If F013 is later un-deferred, 012.2's changes are forward-compatible — `frame_type`
and context enrichment carry over directly. `await_result` becomes a single-frame
special case of the sync barrier. Guardrails extend naturally to any future sub-agent model.
