# 012.3 — Programmatic Tool Calling

**Status:** Ready  
**Estimated effort:** ~2-3 hours  
**Branch:** `feat/012.3-programmatic-tool-calling`

## Motivation

Nous currently calls memory tools one at a time — each `recall_deep` or `recall_recent`
invocation is a separate model round-trip. For multi-recall workflows (e.g. "what do I know
about X across facts, decisions, and recent episodes?"), this means 3+ round-trips through
the model before Claude has the information it needs.

Anthropic's `code_execution_20260120` tool allows Claude to write Python code that calls
tools programmatically in a sandbox. Instead of:

```
turn 1: recall_deep("facts about X") → model → result
turn 2: recall_recent() → model → result  
turn 3: recall_deep("decisions about X") → model → result
turn 4: synthesize and respond
```

Claude can write a script, run all three lookups in one shot, filter the results, and
return only the relevant slice to reason over:

```
turn 1: code_execution script calls all 3 tools, filters results → model synthesizes → respond
```

Anthropic benchmarks (BrowseComp, DeepSearchQA) show this is the single biggest
unlock for multi-step agent performance.

## Scope

Minimal, surgical change. Three parts:

1. **Add `code_execution_20260120` tool** to the tools payload
2. **Mark read-only tools** with `allowed_callers` 
3. **Handle code execution result blocks** in the runner tool loop

No new DB tables. No schema changes. Feature-flagged via config.

## `allowed_callers` Semantics

The `allowed_callers` field controls who can invoke a tool:
- `["direct"]` — only Claude can call it directly (default if omitted)
- `["code_execution_20260120"]` — only callable from within a code execution script
- `["direct", "code_execution_20260120"]` — callable both directly and from scripts

## Tool Exposure Matrix

| Tool | `allowed_callers` | Reason |
|------|-------------------|--------|
| `recall_deep` | `["direct", "code_execution_20260120"]` | READ — main batch use case |
| `recall_recent` | `["direct", "code_execution_20260120"]` | READ — main batch use case |
| `list_tasks` | `["direct", "code_execution_20260120"]` | READ — batch status checks |
| `learn_fact` | `["direct", "code_execution_20260120"]` | WRITE — useful for batch fact extraction; reversible |
| `record_decision` | omit (default `["direct"]`) | Needs deliberation, not scripting |
| `create_censor` | omit (default `["direct"]`) | Behavior change, explicit intent only |
| `spawn_task` | omit (default `["direct"]`) | Side effects, could cause runaway tasks |
| `schedule_task` | omit (default `["direct"]`) | Side effects |
| `cancel_task` | omit (default `["direct"]`) | Destructive |

## Implementation

### Part 1: Config flag

`nous/config.py` — add one setting:

```python
programmatic_tools_enabled: bool = Field(
    default=False,
    description="Enable code_execution_20260120 for programmatic tool calling (beta)",
)
```

Env var: `NOUS_PROGRAMMATIC_TOOLS_ENABLED=true`

### Part 2: Tool registration (`nous/api/tools.py`)

Add `allowed_callers` to the schemas of tools that should be accessible from code execution.
Note: `["direct", "code_execution_20260120"]` is required for tools to work BOTH ways.
Omitting the field (default) means model-only — code execution cannot call it.

```python
# recall_deep, recall_recent, list_tasks, learn_fact
_RECALL_DEEP_SCHEMA: dict[str, Any] = {
    "type": "object",
    ...
    "allowed_callers": ["direct", "code_execution_20260120"],
}

_RECALL_RECENT_SCHEMA: dict[str, Any] = {
    "type": "object",
    ...
    "allowed_callers": ["direct", "code_execution_20260120"],
}

_LIST_TASKS_SCHEMA: dict[str, Any] = {
    "type": "object",
    ...
    "allowed_callers": ["direct", "code_execution_20260120"],
}

_LEARN_FACT_SCHEMA: dict[str, Any] = {
    "type": "object",
    ...
    "allowed_callers": ["direct", "code_execution_20260120"],
}

# record_decision, create_censor, spawn_task, schedule_task, cancel_task
# → no allowed_callers field (default: model-direct only)
```

### Part 3: Inject code_execution tool (`nous/api/runner.py`)

In `ToolDispatcher.available_tools()` (or wherever tools are assembled for the API payload),
prepend the code execution tool when the feature flag is on:

```python
def available_tools(self, frame_id: str) -> list[dict[str, Any]]:
    tools = [...]  # existing logic
    if self._settings.programmatic_tools_enabled:
        tools = [{"type": "code_execution_20260120", "name": "code_execution"}] + tools
    return tools
```

### Part 4: Handle code execution blocks in tool loop (`nous/api/runner.py`)

The runner's streaming tool loop currently only handles `tool_use` blocks. Code execution
emits different event types that need to be passed through. In the streaming loop, add
handling for `code_execution_input`, `code_execution_output` block types:

```python
elif event.type == "content_block_start":
    block = event.content_block
    if block.get("type") == "code_execution_input":
        # Claude is writing a tool script — log for debug, no action needed
        logger.debug("Code execution script started")
    elif block.get("type") == "code_execution_result":
        # Script ran — results are automatically fed back to Claude
        # Log for observability
        logger.debug("Code execution result received")
```

The Anthropic SDK handles the sandbox execution and result injection automatically —
Nous doesn't need to run the sandbox itself. The SDK executes the script, calls our
registered tools (via `allowed_callers`), and returns results in the message stream.

## What Changes

```
nous/config.py              +1 setting (programmatic_tools_enabled)
nous/api/tools.py           +4 lines (allowed_callers on 4 schemas)
nous/api/runner.py          +~15 lines (inject tool + handle new block types)
nous/handlers/             no changes (bypass runner — see Episode Summarizer note)
```

Subtask worker benefits automatically — no separate changes needed.

No DB migrations. No new dependencies. Fully backward-compatible (feature off by default).

## Subtask Behavior

Subtasks run through the same runner as main turns, so programmatic tool calling applies
automatically when the flag is on — no extra implementation needed.

**Where it helps subtasks most:**

- **Research subtasks** — batches `recall_deep` + `recall_recent` before reasoning instead
  of interleaving round-trips with synthesis
- **Batch write subtasks** — a task that extracts and stores multiple facts can script all
  `learn_fact` calls in one shot rather than one round-trip per fact
- **Decision review subtask (Tier-2)** — can fetch N decisions, evaluate all, return a
  structured report without N model round-trips

Same tool exposure policy applies in subtask context (identical `allowed_callers` matrix).
Recursive task spawning via `spawn_task` from code execution is intentionally excluded —
that's a separate feature (012.4 territory) and needs a depth limit first.

## Episode Summarizer / Fact Extractor

These handlers (`episode_summarizer.py`, `fact_extractor.py`, `knowledge_extractor.py`)
currently make **direct httpx calls** to the Anthropic API — they bypass the runner entirely.
They prompt → parse JSON → write to Heart directly. **Programmatic tool calling does not
apply to them in this release.**

To benefit, they would need to run as agent subtasks through the runner (with tools exposed).
That would unlock:

- `recall_deep` before `learn_fact` to dedup against existing facts before storing (currently
  done with a separate DB query, could be unified into the LLM script)
- Batch `learn_fact` calls in one code execution script

This is a worthwhile future refactor but out of scope for 012.3. Track as a follow-on.
