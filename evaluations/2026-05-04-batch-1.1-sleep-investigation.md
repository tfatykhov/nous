# 2026-05-04 — Sleep phases investigation (EXEC-PLAN 1.1)

**Branch:** `tune/memory-recall-and-sleep`
**Plan item:** [EXECUTION-PLAN](EXECUTION-PLAN.md) §1.1 (sleep phases broken)
**Outcome:** **No code bug.** Phases are firing correctly. The
"silent failure" was a probe-side measurement gap. Shipped a probe
improvement (REFUSED verdict) so the same misdiagnosis can't recur.

## What the audit said

`eval_sleep_cycle_health.md` showed `stale_scan` and
`cluster_consolidation` at zero work for **14 consecutive sleep cycles**.
Audit flagged this as critical anomaly #1: "Sleep phases silently
broken." Recommended action: investigate the gap between
`filter_dryrun` (GREEN with eligible candidates) and `cycle_health`
(RED with zero output).

## What we found

**Both phases are firing correctly.** The "silent failure" is a
disambiguation gap in the cycle-health probe.

### stale_scan

`eval_sleep_filter_dryrun.md` reported: `stale_scan GREEN (0
candidates, no genuinely stale facts)`. The probe's selection SQL
(probe code line 159-169) is byte-identical to the production phase's
SQLAlchemy filter (`sleep_handler.py:1047-1068`). When the probe says
"no stale facts," that's correct — the phase has nothing to deactivate.

The "zero deactivations for 14 cycles" is correct behavior on a corpus
with no genuinely stale facts. The cycle_health probe's threshold
(`zero_warn_after=7`) doesn't account for "intentionally zero on a
corpus with no work to do."

### cluster_consolidation

`eval_sleep_filter_dryrun.md` reported: `cluster_consolidation GREEN
(13 eligible clusters)`. So clusters DO exist — the phase has work
available.

`eval_sleep_action_audit.md` (same agent, 1-day lookback) shows **5
`f027_cluster_merge` events** with quality 50% (2 correct, 2 wrong, 1
ambiguous). So events ARE being emitted in production sleep cycles.

But `eval_sleep_cycle_health.md` shows `clusters_merged=0` for 14/14
cycles. How can both be true?

Reading `_phase_cluster_consolidation` (sleep_handler.py:1092-1314):

- The phase iterates clusters, calls the LLM, and emits a
  `f027_cluster_merge` event for **every outcome** (success,
  LLM-refused, LLM-malformed, admission-rejected). Lines ~1209-1230.
- `merged_count` only increments on the success path (line 1308),
  after the merged fact is admitted and the originals are
  deactivated.
- `sleep_stats["clusters_merged"] = merged_count` (line 1312) — only
  successful merges count.

So all 5 audit events were LLM_REFUSED or REJECTED_BY_ADMISSION
outcomes; zero merges succeeded; the counter stays 0.

This is **the same pattern as F031 / F026 in earlier batches** — the
audit's interpretation was wrong. Phases work as designed; the
measurement signal didn't distinguish "phase didn't fire" from "phase
fired but every attempt failed."

### Why the LLM refuses every cluster

Today's F027 v4 sonnet eval (`f027_supersession_eval_v4_sonnet_canonical.md`)
showed 85% overall accuracy on synthetic data. Production data is
messier — the dry-run found 13 eligible clusters but their content
likely includes accumulating subjects (lessons_learned, names) where
refusing IS the correct call. The 50% quality verdict in
`sleep_action_audit` confirms judges agreed with about half the LLM's
calls.

Net: this is a **prompt + data quality issue**, not a silent failure.

## What we shipped

A probe improvement (`nous_eval/probes/sleep_cycle_health.py`) that
distinguishes "phase fired and refused" from "phase didn't fire":

### New `event_type` field on `PhaseSpec`

Phases that emit per-action events now declare the event type:

```python
PhaseSpec("cluster_consolidation", "clusters_merged",
          "F027 merge clusters of similar facts into one",
          event_type="f027_cluster_merge"),
```

### New `fetch_phase_event_counts()` helper

Queries `nous_system.events` for the per-phase event counts in the
same window as the sampled cycles.

### New `REFUSED` verdict

When `zero_streak >= zero_warn_after` AND `event_count > 0`, the phase
is reported as `REFUSED` instead of `RED`:

```
cluster_consolidation: 14 consecutive zeros, but 5 f027_cluster_merge
events emitted — phase IS firing; LLM refusing or admission rejecting
every attempt
```

`overall_exit_code` treats `REFUSED` as informational (does not block
CI), so on-call doesn't get paged for prompt-quality issues.

The report renderer surfaces `REFUSED` phases in a separate section
with a pointer to `sleep_action_audit` for triage:

```
REFUSED phases (firing but no successful work — prompt/data quality
issue, not silent failure):
  - cluster_consolidation: ...
      triage via sleep_action_audit (judges per-event correctness)
```

### Tests

`tests/test_sleep_cycle_health_probe.py` — 4 new tests (18 total, all
pass):

- `test_analyze_phase_refused_when_zero_streak_but_events_emitted`
- `test_analyze_phase_red_when_no_events_emitted_either`
- `test_analyze_phase_red_when_no_event_type_declared`
- `test_overall_exit_code_refused_does_not_block`

## Decision

**No production code change.** Sleep handler's `_phase_stale_scan`
and `_phase_cluster_consolidation` are correct. The fix was at the
probe layer.

`stale_scan` continues to surface as RED on this specific corpus
because dry-run reports 0 candidates → no events to elevate to
REFUSED. That's correct behavior; the probe's bound is just calibrated
for active corpora that should have stale facts. Per-agent override
already exists (`_AGENT_OVERRIDES`); operators can raise the bound on
corpora where stale-fact accumulation is intentionally low.

## Lessons (carry forward)

This is the **fourth** time in two days that an audit-flagged "code
bug" turned out to be a measurement/eval-fixture gap:

| audit item | actual cause | fix location |
|---|---|---|
| F031 REMOVE 20% accuracy | Haiku gen-prompt uses mutable properties | eval gen prompt (queued) |
| F026 ActionGate dup detection | repetition-blocking by design | per-action threshold (queued) |
| F051 baseline drift | audit conflated ce_off vs baseline | nothing — measurement clarity |
| **Sleep phases broken** | counter only counts success; refused outcomes invisible | probe distinguishes REFUSED |

Pattern to standardize: **before claiming a code bug, inspect the
measurement.** The 4 cases above would have triggered ~10 days of
speculative refactoring; investigation in 1-2 hours each surfaced
the real cause. Add this to EXEC-PLAN process change 4.x as a
standing ritual.
