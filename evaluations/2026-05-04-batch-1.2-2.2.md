## Item 1.2 — F031 REMOVE actions

### What the audit said

F031 contradiction-resolver scored 20% on REMOVE_A and REMOVE_B across 3 iterations. Best overall: 53% (v3). Audit recommended: restrict action vocabulary to `{SUPERSEDE, KEEP_BOTH}` or rework the prompt.

### What we found

**The resolver is making defensible calls.** The eval failures are a fixture-generation problem, not a classifier problem.

Inspected `reports/f031_resolution_eval_v3.json` REMOVE_A failures. The Haiku-generated "B" facts that should have ground-truth REMOVE_A actually look like state changes:

| ground truth | Haiku-generated B | resolver picked | resolver's reason |
|---|---|---|---|
| REMOVE_A | "API rate limit changed" | (downgraded to KEEP_BOTH; conf 0.72) | "rate limits are mutable" |
| REMOVE_A | "Telegram bot token expiration date changed" | downgraded | "token expiration dates are mutable" |
| REMOVE_A | "PR #380 fixed 5 findings" (vs A: "fixed 3") | downgraded | "direct numerical contradiction" |
| REMOVE_A | "DAG node default timeout changed" | downgraded | "same date, same property → mutable" |

The REMOVE generation prompt asked Haiku to produce "OBJECTIVELY WRONG (factual error, not state change)" pairs. Haiku failed: it produced facts using mutable-looking properties (rate limits, expiration dates, counts, timeouts). The resolver correctly classified them as supersession candidates with confidence < 0.7 (which the safety floor downgrades to KEEP_BOTH — exactly the documented conservative behavior).

### Why restricting vocabulary won't help

The confusion-matrix rows for REMOVE_A/B show the model picked SUPERSEDE for 4 of 5 cases. If we drop REMOVE from the vocabulary, the model would still pick SUPERSEDE — and the eval, treating the gold as REMOVE, would still mark them wrong. Same denominator, same numerator, no metric movement.

### Decision

**No code fix.** Mark item 1.2 as resolved-as-eval-issue.

The resolver behavior is correct: ambiguous cases get conservatively downgraded to KEEP_BOTH via the 0.7 floor. That's the F031 SAFETY_FLOOR_DESCRIPTION's intent, working as designed.

### Real next step (out of scope for this batch)

Improve `scripts/eval/eval_f031_resolution.py::_GEN_PROMPTS["REMOVE_A"]`:

- Force generators to use **immutable factual-error properties** (math, geography, definitions, historical facts) rather than mutable state
- Add explicit examples in the gen prompt: "Pi equals 3.14" vs "Pi equals 4" → REMOVE; not "rate limit was 100" vs "rate limit is 200"
- Re-run after gen-prompt fix; expect REMOVE accuracy to lift substantially

This is a methodology fix, not an audit-critical fix. Tracked under EXEC-PLAN process change 4.2 (judge sensitivity ritual) → broader category of "fixture-quality regressions."

## Item 2.2 — F026 ActionGate post-#285

### What the audit said

F026 ActionGate scored 9/12 (75%). 3 failures all involved duplicate detection:

- `write_exact_duplicate_blocked`
- `learn_fact_duplicate_blocked`
- `schedule_exact_duplicate_blocked`

Audit recommended: re-run against post-PR-#285 ActionGate; if still failing, lower threshold or add exact-content short-circuit.

### What we found

Re-ran with current code: **same 3 failures** with same reasons. But the reasons reveal **by-design behavior**, not a missed PR-#285 fix:

| failure | reason | meaning |
|---|---|---|
| `write_exact_duplicate_blocked` | `under-threshold(1/6)` | ActionGate requires **6+ occurrences** to block; eval has 1 |
| `learn_fact_duplicate_blocked` | `under-threshold(1/3)` | Requires **3+ occurrences**; eval has 1 |
| `schedule_exact_duplicate_blocked` | `no-duplicates` | Schedule actions aren't tracked for dedup at all |

ActionGate is **repetition-blocking** (block on N+ occurrences within a turn window), not **uniqueness-blocking** (block on any 2nd occurrence). PR #285's "ALL-match + turn window" tightening is in place; it just doesn't trip on the 1-occurrence test setup.

### Decision

**No code fix.** ActionGate is working as intended. The eval test expectations don't match the gate semantics.

### Real next step (out of scope for this batch)

Two paths to choose between in a follow-up:

- **A.** Update test expectations to match repetition semantics (1-occurrence cases should expect `approved=True`, not `False`). Cheapest.
- **B.** Add an exact-content short-circuit before the threshold check for irreversible high-stakes actions (`learn_fact` writes to DB; `schedule` creates a recurring task). Add a new `f026_exact_dup_blocked` test category with N=1 expectations.

Recommend **B** — for `learn_fact` and `schedule`, even 1 exact duplicate is wasteful (creates duplicate row / duplicate cron). Bash and write_file may be legitimately repeated (different cwd, different content with same name). Per-action threshold tuning.

Tracked under EXEC-PLAN process change 4.4 (per-relation regression assertions) → similar shape: per-action threshold tuning vs blanket gate.

## Item 1.5 — Context-packing MMR gate (added later in same session)

### What the audit said

`eval_context_packing_mmr_forced` lifted pass rate 25% → 75% by
"forcing MMR." Audit framed this as "production gates MMR per-scenario
in `cognitive/context.py`." Recommended: investigate the gate.

### What we found

**No per-scenario gate exists.** `mmr_enabled` is a global Settings
flag with default `False`. The audit's framing was wrong. The real
constraint is `mmr_enabled=False` + `mmr_skip_after_ce=True` defaults
together: MMR never runs.

### What we tried

Flipped `mmr_enabled` default to True. Measured retrieval to confirm
F030.1 protection (mmr_skip_after_ce=True keeps retrieval safe when CE
is on). Determinism check: PASS. Re-ran F051 retrieval matrix:
identical metrics on both corpora — F030.1 protection works as
designed.

But context-packing eval still showed 33% — same as default. Reason:
local `.env` has `NOUS_MMR_ENABLED=false` overriding the code default.
Re-ran with explicit env override; still 33%. The lift only appeared
when ALSO setting `mmr_skip_after_ce=False` (so MMR runs after CE).

### Trade-off measured

| metric | flags-off | both-on | Δ |
|---|---:|---:|---:|
| nous_prod retrieval MRR | 0.828 | 0.797 | **-3.7%** |
| nous_prod retrieval nDCG | 0.851 | 0.816 | -4.1% |
| nous_prod retrieval R@10 | 0.922 | 0.878 | -4.8% |
| longmemeval retrieval MRR | 0.892 | 0.931 | +4.4% |
| longmemeval retrieval R@10 | 0.389 | 0.338 | **-13.1%** |
| longmemeval retrieval nDCG | 0.478 | 0.452 | -5.4% |
| **context-packing memory bucket** | 33% | **100%** | **+67pp** |

### Decision

**Roll back the default flip.** F030.1 was correct for retrieval; the
audit's hypothesis about a "gate" was incorrect; a single global flag
can't satisfy both retrieval and context-packing optimization at once.

The right fix is **per-consumer MMR control**: pass an `mmr_override`
kwarg through `recall_deep` → `Heart.recall`. Context-packing consumers
(`run_recall_pipeline` callers in eval, downstream LLM context
assembly) opt MMR on; raw retrieval (`recall_deep` tool) keeps current
default. Plumbing is medium effort; tracked as follow-up.

### Why this is a useful finding even though no code shipped

1. **Quantifies the F030.1 trade-off.** The original F030.1 work measured retrieval MRR; this measures the cost on context completeness. We now have both numbers.
2. **Falsifies the audit's "gate" framing.** The audit was wrong about *where* the suppression happens. Real cause: defaults, not a gate.
3. **Defines the right architecture.** Per-consumer MMR is the proper fix; before this measurement we'd have shipped a global flip and silently regressed retrieval.

## Lessons

1. **Inspect failure modes before "fixing" the code.** Both items looked like classifier bugs; both were fixture-design issues. The 75-min batch saved a 2-3-day rework cycle.
2. **The audit's "REMOVE 0%/20% accuracy" headline number was real but misleading** — it described a *real* eval result without distinguishing "model wrong" from "fixture wrong." Standardize this: every per-category accuracy report should sample 2-3 failures and check whether the model's pick is defensible.
3. **For repetition-based gates, the test fixture must match the gate's window semantics.** ActionGate's threshold isn't gameable from a 1-shot test; need fixtures with N>=threshold to validate blocking.
4. **Forge memory was load-bearing** — surfaced that F027 sonnet eval already happened pre-prompt-fix, prevented redundant work. Same memory is the reason this batch closed in 75 minutes vs 2-3 days of speculative refactoring.
