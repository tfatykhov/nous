## Critical anomalies (act now)

### 1. Two sleep phases silently broken for 14 consecutive cycles

> **UPDATE 2026-05-04:** Investigated; **no code bug**. Both phases
> are firing correctly. The "silent failure" was a probe-side
> measurement gap. Reading `_phase_cluster_consolidation` revealed
> that `clusters_merged` only increments on the SUCCESS path, while
> events emit on every outcome (success/refused/malformed/rejected).
> sleep_action_audit shows 5 cluster_merge events in 1 day → phases
> ARE firing; the LLM is just refusing every attempt (corpus has
> accumulating subjects where refusing IS correct). For stale_scan,
> `eval_sleep_filter_dryrun` confirms "0 candidates, no genuinely
> stale facts" — zero deactivations is correct behavior on this
> corpus. **Fix:** added `REFUSED` verdict to `sleep_cycle_health`
> probe so "phase fired but every attempt failed" is distinguished
> from "phase didn't fire." 4 new tests, 18/18 pass. Detail:
> [`2026-05-04-batch-1.1-sleep-investigation.md`](2026-05-04-batch-1.1-sleep-investigation.md).

`reports/eval_sleep_cycle_health.md` (2026-05-03) tracks 14 sleep
cycles from 2026-04-27 → 2026-05-03 and surfaces:

- **`stale_scan`**: 0 facts deactivated, 14/14 cycles. The phase has
  been completely inactive for a week.
- **`cluster_consolidation`**: 0 clusters merged, 14/14 cycles. Same
  silent failure window.

**Contradiction with dry-run**: `reports/eval_sleep_filter_dryrun.md`
(same date) reports BOTH phases as GREEN with eligible candidates
(13 clusters in `cluster_consolidation`, no genuinely-stale facts in
`stale_scan` — but the latter could be eval-corpus-specific). So the
filters work in dry-run mode but the actual cycles produce zero work.

**What this means**: Memory-management hygiene has been silently OFF.
Orphan facts accumulate, contradictions don't get pruned, clusters
don't merge. The F053 dead-edge prune we just shipped will run, but
the upstream phases that generate "should-be-pruned" candidates
aren't firing.

**Action**: Investigate the gap between filter_dryrun (GREEN) and
cycle_health (RED). Likely root cause is a runtime gate (admission
filter, settings flag, or unhandled exception) silently no-op'ing
the phase body. Compare `_phase_stale_scan` and
`_phase_cluster_consolidation` execution paths against the dry-run
selection SQL.

### 2. F031 contradiction-resolver REMOVE semantics broken

> **UPDATE 2026-05-04:** Investigated; **no code fix shipped**. The
> "20% REMOVE accuracy" turned out to be a fixture-generation bug, not
> a classifier bug. The Haiku-generated REMOVE_A pairs use mutable-
> looking properties (rate limits, expiration dates, counts, timeouts);
> the resolver correctly identifies them as supersession candidates
> with confidence < 0.7, which the safety floor downgrades to KEEP_BOTH
> (intended conservative behavior). Restricting vocabulary won't help
> because the model would still pick SUPERSEDE for those rows; the eval
> would still mark them wrong against the gold REMOVE label. Real fix:
> rewrite the gen prompt to use immutable factual-error properties
> (math, geography, definitions) — methodology task, not audit-critical.
> Detail: [`2026-05-04-batch-1.2-2.2.md`](2026-05-04-batch-1.2-2.2.md).

`reports/f031_resolution_eval_v3.md` (latest, best of 3 iterations):

| action | accuracy | n |
|---|---:|---:|
| SUPERSEDE_A | 80% | 5 |
| SUPERSEDE_B | 100% | 5 |
| MERGE | 20% | 5 |
| KEEP_BOTH | 80% | 5 |
| **REMOVE_A** | **20%** | 5 |
| **REMOVE_B** | **20%** | 5 |

Best-case overall: **53%**. Earlier iterations: 33% / 37%.

Both REMOVE actions hover at 20% accuracy across all 3 iterations —
the resolver fundamentally cannot distinguish "delete this fact" from
"supersede with the other one." MERGE collapsed in v3 (40% → 20%)
without obvious cause. PR #412 fixed the chain-preservation bug but
the underlying decision quality is poor.

**Action**: F031 needs a rethink — either prompt rework, separate
classifier per action type, or restrict the action vocabulary to
{SUPERSEDE, KEEP_BOTH} until REMOVE/MERGE quality recovers. The
0.7-confidence floor in `sleep_handler.py:668` currently downgrades
low-conf actions to KEEP_BOTH which masks this in production.

### 4. F051 retrieval baseline drifts — possibly two different baselines

> **UPDATE 2026-05-04:** Determinism check (closes EXECUTION-PLAN 1.4)

> with byte-identical retrieved IDs across runs. The "0.810 vs 0.828"

> from Apr 29 → May 2 remains real (qrel set grew 40 → 90 + scoring

config 3× and asserts byte-identical outputs.

### 5. Context packing catastrophically failing under strict judge

> **UPDATE 2026-05-04:** Investigated; the audit's framing of a
> "per-scenario MMR gate" was wrong — there is no such gate. The
> real cause is `mmr_enabled=False` + `mmr_skip_after_ce=True`
> defaults: MMR never runs in production. Tried flipping both flags
> on and measured: context-packing memory bucket lifts 33% → **100%**
> (+67pp) BUT nous_prod retrieval MRR drops 0.828 → **0.797** (-3.7%)
> and longmemeval R@10 drops 0.389 → 0.338 (-13.1%). F030.1's
> `mmr_skip_after_ce=True` decision is correct for retrieval and
> wrong for context packing. **Reconciliation:** per-consumer MMR
> control. Context-packing consumers should force MMR on; raw
> retrieval consumers (recall_deep tool) keep current default.
> Requires plumbing an `mmr_override` kwarg through `recall_deep` →
> `Heart.recall`. Defer until that refactor lands. Defaults rolled
> back to F030.1 baseline. Detail:
> [`2026-05-04-batch-1.2-2.2.md`](2026-05-04-batch-1.2-2.2.md).

`reports/eval_context_packing.md`: **0/8 (0%) PASS** under strict
judge. Loose judge: **4/8 (50%)**. Forced MMR everywhere: **6/8 (75%)**.

| variant | pass rate | notes |
|---|---:|---|
| strict, top-k baseline | 0/8 | every scenario insufficient |
| strict + baseline tweaks | 2/8 | procedure_learning, graph_densification only |
| loose judge, top-k | 4/8 | + telegram_email, heartbeat_overview, rubric_evolution |
| strict + MMR enabled | 2/8 | identical to baseline (MMR not active per-scenario) |
| **strict + MMR forced** | **6/8** | **+ skill_management, subtask_workers, cognitive_loop** |

**The fix is sitting in plain sight**: forcing MMR across all
scenarios takes us from 25% to 75% pass. But the production default
is "MMR sometimes" (gated on conditions in `cognitive/context.py`).

**Action**: Investigate why production's per-scenario MMR gate
suppresses the lift. Either (a) the gate is wrong, or (b) MMR
forcing has a side-effect (latency? memory?) we haven't measured.
This contradicts the F030.1 / today's MMR finding that MMR HURTS
retrieval MRR — context packing is downstream of retrieval, so the
right MMR setting may be different at the two stages.

### 7. F026 ActionGate duplicate detection silently weak

> **UPDATE 2026-05-04:** Re-ran F026 against current code. Same 3 fails;
> reasons (`under-threshold(1/6)`, `under-threshold(1/3)`, `no-duplicates`)
> reveal these are **by-design repetition semantics**, not a missed
> PR-#285 fix. ActionGate blocks repetition (N+ occurrences in a turn
> window), not first-time exact duplicates. Test expectations don't
> match gate semantics. No code fix shipped. Real next step: per-action
> threshold tuning — for `learn_fact` and `schedule` (irreversible writes),
> add an exact-content short-circuit at N=1; for `bash` and `write_file`
> (legitimately repeatable), keep the threshold-based design. Detail:
> [`2026-05-04-batch-1.2-2.2.md`](2026-05-04-batch-1.2-2.2.md).

`reports/f026_eval.md`: ClaimVerifier 18/20 (90%), ActionGate 9/12 (75%).
All 3 ActionGate failures involve duplicate detection:

- `write_exact_duplicate_blocked`: should-block=True, actual=False
- `learn_fact_duplicate_blocked`: should-block=True, actual=False
- `schedule_exact_duplicate_blocked`: should-block=True, actual=False

The threshold is too lenient — exact duplicates aren't being caught.
PR #285 reportedly tightened ActionGate dedup (ALL-match + turn
window), but this eval suggests the change isn't catching the
synthetic duplicate scenarios.

**Action**: Re-run F026 against the post-#285 ActionGate. If the
fails persist, lower the dedup threshold or add an exact-content
short-circuit before the LLM tier.

### 9. Compaction introduces 26.7% hallucinations / contradictions

`reports/eval_compaction_fidelity.md`: 33/45 facts preserved (73.3%)
across 15 scenarios. The 26.7% miss rate isn't just "missed facts" —
it includes:

- **Fact fabrication**: summary invents "David Park" (not in source)
- **Wrong values**: "us-east-1" claimed when source said "us-east-2"
- **Contradictions**: "Redis Streams" claimed but source says
  "Postgres LISTEN/NOTIFY"
- **Missing entities**: Priya Patel never mentioned but appears in
  compaction

These aren't omissions — they're false claims. Compaction is unsafe
for facts that downstream code reads back literally.

**Action**: Add a compaction post-check that diffs source-vs-summary
named entities and rejects any entity in the summary that isn't a
substring of the source. Also surface `compaction_hallucinations`
counter to observability.

## Methodological gaps

### 11. Coverage gaps — these subsystems have NEVER been eval'd

- **sleep_ingestion** (memory intake during sleep): no evals exist
- **deliberation chain-of-thought**: no reasoning trace analysis
- **decision closure & outcome feedback**: no decision review eval
- **skill auto-learning effectiveness**: no quality metric on
  newly-created skills
- **retrieval pre-RRF tuning** (BM25 weights, hybrid weights):
  no ablation
- **fact-graph edge recall** (only precision is measured): we
  know we don't link some pairs we should but no metric on it

### 12. Underrepresented surfaces

- **memory_ingestion**: 2 reports (compaction + working_memory).
  Missing: deep recall coverage, fact entailment, semantic
  similarity tuning under the F056/F057 changes
- **sleep_action**: 1-day lookback only; no multi-week trend
- **context_packing**: 5 reports but the "forced MMR" winning
  variant isn't integrated into production

### 13. Sample-size weakness

Several validating runs use n=20 (longmemeval) or n=12-15 (memory
ingestion). The +5.2% MRR lift on `ce_off` for longmemeval is
based on 20 questions — wide CIs. Would not hold up to a
5-question subset shift. The eval framework should bootstrap CIs
or require n>=50 for "shipped" decisions.

### 14. Judge-model sensitivity not normalized

F027 showed 20pp variance under different judge models. Other LLM-
judged evals (compaction_fidelity, anti_hallucination) use a single
judge without sensitivity analysis. Ship a "judge sensitivity"
ritual for any new LLM-judged metric: re-run with a stronger model,
report the gap.
